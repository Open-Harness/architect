## The idea

A store is a place where things live. One rule decides what counts: **a place is a store when Orthograph owns its schema
and every write to it goes through Orthograph's commit.** The commit takes everything one call changes (its writes, the
events its move recorded, and the answer kept under its request key) and lands all of it or none of it, guarded by a
version. The kinds of store are open. A host or a language supplies a kind by implementing one port. Orthograph ships
`database` and `actor`. A chain is a host, and the store kind it runs is `chain` (K3 item 2). K7 and K25 decided its details: a chain store is a file, its commit answers late with a submission, and it is built in M6.10 ([chains-and-wallets](chains-and-wallets.mdx)).
KV, R2 and caches can't take that commit, so a thing never lives in one. A
database someone else owns isn't a store either: it is a source, and you reach it through an adapter.

## The smallest example

Acme's allowance says nothing about where it lives:

```ts file=examples/acme/blueprint/things/allowance/thing.ts name=Allowance lines=6-15
export const Allowance = Blueprint.thing({
  description: "Money a member may spend from their organisation, up to a limit each month.",
  fields: {
    id: Blueprint.id("alw"),
    organization: Organization.fields.id,
    member: Person.fields.id,
    limit: Amount,
    spent: Amount,
  },
});
```

So it lives in the project's default store, a `database`. The compiled model says so, and this table is rendered
from it, not written:

The local environment binds that store to D1, emulated on your machine:

```ts file=examples/acme/blueprint/environments/local.ts name=default lines=3-8
export default Blueprint.environment({
  runs: "on this machine",
  identity: Identity.testPrincipals, // fixed test people, no sign-in
  database: Cloud.d1.local(), // the local runtime emulates D1: no database process
  telemetry: [Telemetry.sink.local()], // prove's Collector, a process of its own
});
```

That is all a one-database app ever writes. To keep a group of things apart, you declare a store and point them at
it. Its name is its path, `ledger`:

```ts planned=M1.17 path=blueprint/stores/ledger.ts
export default Blueprint.store.database();
```

```ts planned=M1.17 path=blueprint/things/entry/thing.ts
import ledger from "../../stores/ledger.ts";
export default Blueprint.thing({ description: "An entry in the ledger.", fields: { id: Blueprint.id("ent") }, lives: ledger });
```

## How it works

### One call, one commit

A handler never writes to a store. It writes to `Records`, which holds every write back until the call ends. Then
the handler wrapper makes one commit and looks at the one thing it returns:

```ts file=packages/language-effect/src/modules/handler/service.ts name=serve lines=134-143
const writes = yield* unit.writes;
const committed = yield* store.commit({ writes, entries, ...request }).pipe(
  Effect.tap((outcome) => Effect.annotateCurrentSpan({
    "commit.outcome": outcome,
    // The event the move emitted, named only on the commit that journalled it: a conflicted attempt emitted nothing.
    ...(outcome === "committed" && entries[0] !== undefined ? { "event.name": entries[0].event } : {}),
  })),
  spanned(`${name}.commit`, { "step.kind": "commit", "commit.writes": writes.length, "commit.entries": entries.length }),
);
if (committed === "conflict") return yield* new Conflict();
```

What goes in, and what comes back, is the port every store kind implements:

```ts file=packages/language-effect/src/modules/records/types.ts name=Commit,Committed lines=32-41
/** Everything one call changes: its writes and the events its move emitted, committed together or not at all. */
export interface Commit {
  readonly writes: ReadonlyArray<Write>;
  readonly entries: ReadonlyArray<Entry>;
  /** For an operation declared `idempotent: "request"`: its answer, kept under its request key in the same commit. */
  readonly request?: { readonly key: string; readonly answer: string };
}

/** `conflict`: an update's version had moved on, so nothing was written and the call runs again. */
export type Committed = "committed" | "conflict";
```

```ts file=packages/language-effect/src/modules/records/types.ts name=Store lines=67-78
/** The host's side. A failing store dies: it is never the caller's refusal. */
export class Store extends Context.Service<Store, {
  /** The rules this store enforces at commit (G5), as the model carries them; a unit made over it looks through the same ones. Absent when the project declares none. */
  readonly rules?: ReadonlyArray<NamedRule>;
  readonly find: (thing: Thing, id: string) => Effect.Effect<Stored | undefined>;
  /** One page of a thing's instances, in the order they were made (never a clock). A thing that lives as actors has none to list. */
  readonly list: (query: ListQuery) => Effect.Effect<Listed>;
  /** `conflict` too when another call committed the same request key first: the retry then finds its answer. */
  readonly commit: (commit: Commit) => Effect.Effect<Committed>;
  /** The answer already committed under a request key, as wire JSON, if there is one. */
  readonly answered: (key: string) => Effect.Effect<string | undefined>;
}>()("@orthograph/language-effect/Store") {}
```

There are only two outcomes. `committed` means the writes, the journal entries and the request's answer all landed.
`conflict` means none of them did, because something else changed one of those things first. A store that fails in
any other way dies: that is a defect, never the caller's refusal.

### The version guard

Every update carries the version this call read. The commit lands only if the stored version is still that one. Each
kind enforces it in its own way. The `database` kind turns a stale version into a NULL on a NOT NULL column, which
fails D1's whole batch:

```ts file=packages/host-cloudflare/src/modules/store/internal/commit.ts name=commitD1 lines=24-25
// The guard: a stale version becomes NULL on a NOT NULL column, which fails the whole batch (D2 #36).
const guard = sql`"version" = CASE WHEN "version" = ${w.version} THEN "version" + 1 ELSE NULL END`;
```

```ts file=packages/host-cloudflare/src/modules/store/internal/commit.ts name=commitD1 lines=33-41
return Effect.gen(function* () {
  const keep = request ? [sql`INSERT INTO "_requests" ${sql.insert({ key: request.key, answer: request.answer })}`] : [];
  const statements = [...(yield* Effect.forEach(writes, statementOf)), ...entries.map(journalOf), ...keep];
  if (statements.length === 0) return "committed" as const;
  return yield* d1.batch(statements).pipe(
    Effect.as("committed" as const),
    Effect.catch((e) => (lostGuard(e) || lostUnique(e, writes, tableOf, rules) ? Effect.succeed("conflict" as const) : Effect.die(e))),
  );
});
```

The `actor` kind has one Durable Object per instance, so it checks the version inside one SQLite transaction:

```ts file=packages/host-cloudflare/src/modules/actors/service.ts name=Actor lines=30-37
return this.ctx.storage.transactionSync((): Committed => {
  const now = this.stored();
  for (const w of writes) {
    if (w.kind === "insert") {
      sql.exec("INSERT INTO instance (one, row, state, version) VALUES (1, ?, ?, 0)", JSON.stringify(w.row), w.state);
      continue;
    }
    if (!now || now.version !== w.version) return "conflict";
```

A `conflict` never reaches the caller. The wrapper runs the whole call again from the top, reading fresh, up to 64
times:

```ts file=packages/language-effect/src/modules/handler/service.ts name=serve lines=168-175
const loop = (number: number, callId: string): Effect.Effect<object, unknown, unknown> =>
  attempt(payload, principal, key, key === undefined ? undefined : request, number, callId).pipe(
    Effect.catch((e) =>
      !(e instanceof Conflict) ? Effect.fail(e)
      : number < ATTEMPTS ? loop(number + 1, callId)
      : Effect.die(new Error(`${name} lost its version race ${ATTEMPTS} times in a row`)),
    ),
  );
```

The request key rides in the same commit, so a retried request can never spend twice. When the second call arrives
with the same key, it finds the first answer and changes nothing:

### A rule is held at commit too

A thing's rules ([invariants](invariants.mdx)) are checked by the runtime before the commit, against the state the call
read. Another call can commit in between, so the store holds each rule as well: one unique index per rule, named after
it, over the rule's key and within its `while` states. Plugged In's `profile` rule has no `while`, so its index covers
every row:

```sql file=examples/plugged-in/generated/server/migrations/0001_things.sql lines=27
CREATE UNIQUE INDEX "profile_onePagePerHandle" ON "profile" ("handle");
```

Of two racing commits, the index refuses the second. The host recognises a failure of one of those indexes, and only
those, and answers `conflict` instead of dying:

```ts file=packages/host-cloudflare/src/modules/store/internal/unique.ts name=lostUnique lines=11-20
export const lostUnique = (error: unknown, writes: ReadonlyArray<Write>, tableOf: (thing: Write["thing"]) => string, rules: ReadonlyArray<NamedRule> = []): boolean => {
  const columns = new Set(writes.flatMap((w) => columnsOf(w.thing, tableOf(w.thing), rules)));
  if (columns.size === 0) return false;
  for (let e: unknown = error, depth = 0; e !== undefined && e !== null && depth < 8; e = (e as { cause?: unknown }).cause, depth++) {
    const message = String((e as { message?: unknown }).message ?? e);
    const failed = /UNIQUE constraint failed: ([^:]+)/.exec(message)?.[1];
    if (failed && failed.split(",").some((c) => columns.has(c.trim().replaceAll('"', "")))) return true;
  }
  return false;
};
```

So a lost race for a name is the same retry as a lost version race. The call runs again, its check finds the winner,
and the runtime refuses with the rule's own error. Any other constraint failure stays a defect. A thing that lives as
actors can't hold a rule: each instance is its own Durable Object, so there is no table to put an index on.

### Why the commit is the test

The rule isn't about which software it is. It is about whether a place can take that commit:

| Place | Why a thing can't live there |
|---|---|
| KV | Writes to several keys can't land together, and there is no version to guard an update with. |
| R2 | An object is written whole, alone. Files are fields kept in R2, not things. |
| A cache | It may drop what it holds. Nothing it holds can be the truth. |
| A search or vector index | It is kept from events and can be rebuilt. It is a kind of view. |
| A database someone else owns | Its other writers never bump our version, so our commits would silently overwrite theirs. Our journal would miss their changes, and our migrations would run against their tables. |

### One call commits to one store

A call's writes all land in its thing's store. The host refuses a commit that writes to more than one store, at run
time:

```ts file=packages/host-cloudflare/src/modules/store/service.ts name=StoreD1 lines=58-59
const owners = new Set(commit.writes.map((w) => ownerOf(w.thing)));
if (owners.size > 1) return Effect.die(new Error("a call wrote to more than one store: one call commits to one store, and work across stores is a workflow (K3 item 5)"));
```

The compiler refuses an operation whose steps write to two stores first, before anything runs (M1.17). Work across stores
runs as a workflow: each step commits to one store, and the workflow remembers which steps are done.

### What a kind can do

A kind declares what it can serve, and the compiler refuses a read the kind can't. An actor holds one instance, so it
has nothing to list, and the compiler already says so:

```ts file=packages/compiler/src/modules/model/internal/describe.ts name=describe lines=226
if (list && t?.thing?.lives === "actor") problems.push(`${file}: a list read needs a thing that lives in the database, and ${thing} lives as actors`);
```

To list things that live as actors, or across stores, declare a view.

### Migrations

Migrations are generated from the model, one set per store, and never for a source: one file per store, with a
version column on every table:

```ts file=packages/projections/src/modules/server/internal/worker-config.ts name=tablesOf lines=59-69
things.map((t) => {
  const columns = Object.keys(t.fields).map((f) => (f === "id" ? `  "id" TEXT PRIMARY KEY` : `  "${f}" TEXT NOT NULL`));
  // Empty until the thing's first move sets it.
  if (t.machine) columns.push(`  "state" TEXT`);
  columns.push(`  "version" INTEGER NOT NULL DEFAULT 0`);
  // A rule (G5) is one partial unique index too, named after it (`<table>_<rule>`) so two rules over one field keep two: over the rule's key, within its `while` states.
  const ruleIndexes = Object.entries(t.invariants ?? {}).map(([rule, { fields, while: states }]) => {
    const scope = states ? ` WHERE "state" IN (${states.map((s) => `'${s.replaceAll("'", "''")}'`).join(", ")})` : "";
    return `CREATE UNIQUE INDEX "${t.name}_${rule}" ON "${t.name}" (${fields.map((f) => `"${f}"`).join(", ")})${scope};`;
  });
  return [`CREATE TABLE "${t.name}" (\n${columns.join(",\n")}\n);`, ...ruleIndexes].join("\n");
```

### Binding a store in an environment

Every store gets the host's default binding: its own D1, named from the store's path. An environment names a store only
when it needs binding differently. The keys are typed from the declared stores, so a misspelt store fails to compile:

```ts planned=M1.17 path=blueprint/environments/local.ts
database: Cloud.d1.local(),                  // the default store, as today
stores: { ledger: Cloud.d1.local() },        // only when it needs saying
```

### Stores that plugins bring

A feature can declare its own stores. Mounted, a store's name is the mount's name plus the store's path, so two
plugins never collide. `@orthograph/auth` keeps Better Auth's tables in a store of its own, and your project never sees
them. That is why stores land in M1: auth in M2 needs them.

## Choices

### Which kind

| | `database` (the default) | `actor` | `chain` (specified, M6.10) |
|---|---|---|---|
| What it is | D1, one row per instance, with a version column | one Durable Object per instance: its own SQLite, its own outbox | a contract, generated in the Solidity language |
| Supplied by | `@orthograph/host-cloudflare` | `@orthograph/host-cloudflare` | `Host.chain`, written for by `@orthograph/language-solidity` (K27) |
| Lists and search | yes | no: declare a view | through views |
| Contention | every call to any instance shares one database | one writer per instance, so instances never contend | one transaction at a time, and every write costs gas |
| Pick it when | you need to list and search across many | an instance takes many writes and needs strict order, and nobody lists them | it is money or a public commitment |

Start with the default. Move a thing to `actor` when one instance is hot and you never list it. Later kinds arrive as
a package each, with nothing else changing: Postgres or MySQL that you own (through Hyperdrive), SQLite on a device for
local-first, Noir on Aztec.

### One store, or several

| | The default store only | A declared store |
|---|---|---|
| What you write | nothing | `blueprint/stores/<name>.ts`, and `lives` on each thing |
| Commits | any operation can touch any of its things in one commit | an operation commits to one store; work across stores is a workflow |
| Migrations | one set | one set per store, ordered per environment |
| Pick it when | almost always | a group of things must be kept apart: a ledger, a plugin's own tables, a store bound differently in production |

## What it is not

- **Not a source.** A database another team runs, like Capxul's bench on MariaDB, is reached through an adapter's
  calls, with typed errors and its own stand-in. Orthograph never migrates it. See `adapters`.
- **Not a view.** A view is a list kept from events, across stores and sources. It can be rebuilt. A store holds the
  truth. See `views`.
- **Not a rule.** A rule is declared on its thing and refused by the runtime; the store only holds it as an index. See `invariants`.
- **Not a table.** A store holds the tables of every thing that lives in it, plus its journal and its kept answers.
- **Not chosen per environment.** The kind is in the model, so it is the same everywhere. Only the binding changes
  per environment. See `environments`.
- **Not a place for files.** A file is a field, kept in R2. See `things`.

  at run time, not by the compiler. A request key on an actor's operation dies: idempotent actors are in
  `design/later.md`.
</Note>

<Note kind="question" id="schema-per-kind" slice="M1.17">
  Where does a kind's schema come from? The store port only reads and commits
  (`packages/language-effect/src/modules/records/types.ts:62`). The schema is hard-coded in the generator, and only for
  D1: every field becomes `TEXT NOT NULL` (`packages/projections/src/modules/server/internal/worker-config.ts:62`). An
  actor keeps the whole instance as one JSON value (`packages/host-cloudflare/src/modules/actors/service.ts:34`). If kinds
  are open, a kind must also say how a thing's fields become its storage, and how that storage migrates.
</Note>

<Note kind="question" id="visibility-per-kind" slice="M1.17">
  What does a field's visibility mean in each kind? Today it is only a comment: Solidity "treats everything as public;
  one that has it, such as Noir on Aztec, uses the roles" (`packages/orthograph/src/modules/visibility/types.ts:1`). So a
  private field on a thing that lives on a chain is either refused by the compiler or silently public. Nothing decides
  which.
</Note>

<Note kind="decision" decision="K7">
  Is a chain a store? Settled by K3 item 2 and K5 seam 2: a chain is a host, and the store kind it runs is `chain`.
  The contract commits per transaction, with one writer. A server call that sends a transaction is a workflow. K7 decided
  that a chain store's own commit may answer late, and its caller
  gets a submission (`simulated` to `confirmed`); how an operation maps to a contract, and the rest of chain storage, are
  K7's and K25's ([chains-and-wallets](chains-and-wallets.mdx)). Aaron's doubt (18 November 2026, said in the canon session on PR #38: "it just doesn't seem like a
  thing that makes sense") is why the pending part moved to the caller.
</Note>

<Note kind="question" id="kind-capabilities" slice="M1.17">
  How does a kind declare what it can serve? The compiler needs it to refuse a read the kind can't serve (lists today;
  search and private state later). The shape of that declaration on the store port is not written yet.
</Note>

<Note kind="question" id="rollback-across-stores" slice="M1.17">
  Rollback is promote of an earlier revision, refused when a migration can't run backwards. With several stores, is
  that decided per store, or does one store's irreversible migration block the whole rollback?
</Note>

<Note kind="question" id="store-binding-keys" slice="M1.17">
  The `stores:` keys in an environment are identifiers checked against generated types. If that reads as writing a
  declared name by hand, the fallback is `Store.bind(ledger, …)`.
</Note>
