## The idea

Every piece of data in an Orthograph system sits in one of four places, and one rule sorts it: **if Orthograph owns
the schema and every write goes through Orthograph's commit, the place is a store. If anything else owns it, it is a
source, reached through an adapter** (K3, "The rule that sorts every case"). A thing **lives** in a store: its `lives`
names one, or says nothing and gets the project's default. A **source** is someone else's data. A **view** is a list
kept from events, ours and a source's, and can always be rebuilt. And **a projection's own state** is data a
projection needs for itself, such as the portal's notes and chat threads: they are things too, in that projection's
own store. Each place has exactly one writer. A store is written only by its commit, a source only by its owner, and a
view only by the events it keeps.

## The smallest example

The sign-up sheet says nothing about where it lives, so it lives in the project's default store:

```ts file=examples/signup/blueprint/things/sheet/thing.ts name=Sheet lines=4-7
export const Sheet = Blueprint.thing({
  description: "A sign-up sheet with a fixed number of places.",
  fields: { id: Blueprint.id("sht"), title: Title, places: Count, taken: Count },
});
```

On Cloudflare the default store is D1. Orthograph writes its schema from the model, and nobody writes it by hand. A
sheet's row carries its fields, its state and the version every commit is guarded by:

```sql file=examples/signup/generated/server/migrations/0001_things.sql lines=3-10
CREATE TABLE "sheet" (
  "id" TEXT PRIMARY KEY,
  "title" TEXT NOT NULL,
  "places" TEXT NOT NULL,
  "taken" TEXT NOT NULL,
  "state" TEXT,
  "version" INTEGER NOT NULL DEFAULT 0
);
```

The same file holds the journal of events and the answers kept under request keys, because they are committed with the
row (`examples/signup/generated/server/migrations/0001_things.sql:12` and `0001_things.sql:23`). The Worker reaches the
database through one binding:

```jsonc file=examples/signup/generated/server/wrangler.jsonc lines=8-10
  "d1_databases": [
    { "binding": "DB", "database_name": "signup", "database_id": "00000000-0000-0000-0000-000000000000", "migrations_dir": "migrations" }
  ],
```

Signup has one store, so it has no source, no view and no projection with state of its own. Those come with the
workshop, from layer 4.

## How it works

### The four places

| Place | Who owns the schema | Who writes it | How a handler reaches it | Explained on |
|---|---|---|---|---|
| a store | Orthograph, from the model | only the commit: one call's writes, its events and its request key, all or nothing | `Records`, inside a step | [stores](stores.mdx) |
| a source | someone else | its owner, never us | an adapter's typed calls, as steps | [adapters](adapters.mdx) |
| a view | Orthograph | only the events it keeps, ours and a source's | the reads generated for it | [views](views.mdx) |
| a projection's own state | the projection | its own operations, through its own store's commit | it is a store, so as above | [portal](portal.mdx) |

### A thing lives in a store

`lives` is the one place a declaration says where a thing's state is. It takes a built-in kind or a declared store,
and the default is a D1 row:

```ts file=packages/orthograph/src/modules/things/types.ts name=Thing,Lives lines=39-64
  /** The kind of place its state is kept: a D1 row with a version column (the default), or a Durable Object per instance (D1 #1). */
  readonly lives: StoreKind;
  /** The declared store it lives in (K3), when `lives` named one; absent for the project's default store. */
  readonly store: Store | undefined;
  /** The prefix of this thing's refusal codes (`AL` in `[AL-002]`); the compiler takes two letters of its name when unset. */
  readonly code: string | undefined;
  /** The runtime's refusal when a call names an instance of this thing that isn't there (K16, M1.46): `<Thing>NotFound`. */
  readonly notFound: NotFound;
  /** A thing with versions (K40 fix 2): one current version per `key`, every save kept, a stale save refused. Absent when it has none. */
  readonly versions: { readonly key: string } | undefined;
}

/**
 * The runtime's own refusal of a missing instance, generated as `<Thing>NotFound` (or the thing's declared error of that
 * name). A journey names it as `Person.notFound`, the way it names a machine's `notFrom`.
 */
export interface NotFound {
  readonly kind: "not-found";
  readonly thing: Thing;
}

/** The kinds of store; open, because a host or a language supplies more (`chain`). */
export type StoreKind = "database" | "actor" | (string & {});

/** What `lives` takes: a word for a built-in kind, or a declared store. Nothing means the project's default store. */
export type Lives = "database" | "actor" | Store;
```

K3 opens that list: a store is declared under `blueprint/stores/`, named by its path, and `lives` takes it. A
one-store app, like signup, changes nothing:

```ts planned=M1.17 path=blueprint/stores/ledger.ts
// blueprint/stores/ledger.ts: the name is the path, "ledger"
export default Blueprint.store.database();

// blueprint/things/entry/thing.ts
import ledger from "../../stores/ledger.ts";
export default Blueprint.thing({ description: "…", fields: { … }, lives: ledger });
```

The kinds are supplied by hosts, and a language writes for them ([languages-and-hosts](languages-and-hosts.mdx)):
`database` (D1) and `actor` (a Durable Object per instance) by the Cloudflare host. A chain is a host too, and the store
kind that runs on it is `chain`, supplied by `Host.chain` and written for by the Solidity language (K27). A thing lives
on a chain by living in a chain store, a file such as `blueprint/stores/budgets.ts` that says
`Blueprint.store.chain.evm()` (K7 Q4, K25). Its commit answers late, with a submission, not `committed` or `conflict` on
the spot (K7). Both are built in M6.10; [chains-and-wallets](chains-and-wallets.mdx) has the whole of it.

### What crosses the edge of a store

One call commits to one store: the compiler refuses an operation whose steps write to two (K3 item 5). Work that
changes two stores, or a store and a chain, is more than one call: each commits to its own store, an event joins them,
and the wait between them is a state of a thing ([machines](machines.mdx), K46). A [workflow](workflows.mdx) is for
durable work that belongs to no single thing (K5 seam 6). A source is never migrated and never committed to. A handler only calls it, through a step the
operation declares, so the call shows in the trace with its declared errors (K3 item 8).

### What stays true among many records

A store holds one row per instance, and some things must be true among all the rows of a thing: one holder per name.
That is declared on the thing, as a rule ([invariants](invariants.mdx)), not on the place it lives, so it moves with the
thing. The store holds it as an index of its own, per rule, generated from the model. Plugged In's two handle rules and
its profile rule become three indexes, the first two on `handle`:

```sql file=examples/plugged-in/generated/server/migrations/0001_things.sql lines=10-11
CREATE UNIQUE INDEX "handle_oneHolderPerName" ON "handle" ("name") WHERE "state" IN ('claimed');
CREATE UNIQUE INDEX "handle_oneNamePerPerson" ON "handle" ("owner") WHERE "state" IN ('claimed');
```

and the third, on `profile`, with no states to name:

```sql file=examples/plugged-in/generated/server/migrations/0001_things.sql lines=27
CREATE UNIQUE INDEX "profile_onePagePerHandle" ON "profile" ("handle");
```

A rule is about the records of one thing, which live in one store. A thing that lives as actors has no table to hold
one, so the compiler refuses a rule on it.

### A projection's own state

Some projections keep data. The portal keeps notes about declarations and chat threads, and neither is part of the
app the developer is building. Both are things in the portal's own store, declared by the portal feature, so they get
the same commit, migrations and journal as the app's own things. A plugin's store is named by its mount plus the
store's path, so it never collides with the app's (K3 item 7). Nothing of agent-native's database comes with it: the
portal's pieces are ported into our own code, over D1 (K5, "Porting from agent-native").

### Seeing all of it

The data map, `generated/data/map.md`, and the portal's data page list every store with its kind, binding and
migrations, every source with its adapter, calls and stand-in, and every view (K3 item 10, slice M5.06).

## Choices

| You have | Put it in | Because |
|---|---|---|
| state your operations change, and the schema is yours | a store, the default unless it must be apart | only a store's commit keeps writes, events and the request key together |
| one instance that many calls change at once | the `actor` kind | each instance commits on its own, so calls on different instances never race |
| data someone else's system owns, such as a bench of candidates or a contract you didn't write | a source, through an [adapter](adapters.mdx) | Orthograph would otherwise migrate or write a schema it doesn't own |
| a list across stores, or across ours and a source's | a [view](views.mdx) | an actor has no list, and a source can't join a query of ours |
| files | a field, with the bytes in R2 | R2 can't take a commit, so it is never where a thing lives |

## What it is not

- **Not where the detail of a commit is explained.** The version guard, migrations, binding a store per environment
  and kinds in depth are on [stores](stores.mdx), in layer 4.
- **Not a "home".** That word is retired: a thing lives in a store (K3, ledger `G-03`).
- **Not a cache, KV or R2.** None of them can take an atomic commit, so no thing lives in one (K3 item 3).
- **Not what stays true among records.** That is a rule, on [invariants](invariants.mdx).
- **Not how a field is hidden.** Who may see a field is visibility, on [things](things.mdx).

## Notes

<Note kind="decision" decision="K3">A place is a store when Orthograph owns its schema and every write goes through
its commit. Anything else is a source, reached through an adapter. The word "home" is retired (ledger `G-03`).</Note>

<Note kind="decision" decision="K5">A chain is a host, and its store kind is `chain`. A server call that sends a
transaction writes two stores, so it is more than one call (K46). K7 settled the rest of chain data: a thing is declared on one by living
in a chain store (K25); its commit returns a submission, because a chain store may answer late; and private state is a
capability of one kind, Aztec's `private`, while a public chain store refuses a secret or private field (ledger `G-04`,
`STO-02` and `X-18`).</Note>

<Note kind="question" id="kind-capabilities" slice="M1.17">A store kind is to declare what it can serve (lists,
search, private state), so the compiler can refuse a read it can't serve. No shape for that declaration exists yet
(ledger `STO-07`).</Note>

<Note kind="decision" decision="K46">
  A thing has four places to live: a database, an actor, a public chain, and a private chain (Aaron, 26 November 2026).
  The fourth is the Aztec store kind K25 sketched, designed and not built. So "is it private?" no longer sends a fact off
  chain by itself. A private fact about something on a public chain can also be a sealed field: our server keeps the
  words, and the chain carries a salted hash of them. On a private store the same field needs no server. Work across two
  places is more than one call, never one commit, and it is a workflow only when no single thing can hold the wait.
</Note>
