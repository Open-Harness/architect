## The idea

A **plugin** is a blueprint someone else wrote, proved in its own CI, and shipped as a package. It is one of five kinds.
The first three answer three questions about a system. A **feature** is what else the system is: its things, operations
and journeys (governance, wallets, auth). An **adapter** is what is outside it: an outside system's calls and events (a
forum, Stripe, a browser wallet). A **projection** is what the system becomes: the API, the SDK, the CLI, the docs, the
portal. K27 adds two more kinds, a **language** and a **host**, for what code is written in and where it runs
([languages and hosts](languages-and-hosts.mdx)); Goal 4 builds them. You use a plugin by **mounting** it: one small
file that says "use this plugin here, like this". Four verbs shape a mount (**choose**, **include**, **narrow**,
**omit**), and every one of them keeps the plugin's proof true. None of this is built yet. It is planned for M1.06 to
M1.13.

## The smallest example

The sign-up sheet mounts no plugins, so it can't show one. Its blueprint is all its own things, and its outputs come
from a fixed list. So this page uses K5's sketch: a governance feature and a forum adapter, one mount file each.

```ts file=design/decisions/K5-the-whole-shape.md lines=443-447
// blueprint/features/governance.ts: the app mounts the reusable feature
export default Blueprint.use(governance, (g) => [g.choose(g.choices.voting.onChain)]);

// blueprint/adapters/forum.ts: the outside forum, its calls and events
export default Blueprint.use(discourse, (f) => [f.include(f.calls.topics.create, f.events.postCreated)]);
```

The feature's mount chooses on-chain voting out of the options governance offers. The adapter's mount names the
forum's one call and one event the app may reach, and nothing else of the forum is reachable. From these two files:

- the feature brings Draft, Revision, Proposal, the publish workflow, their journeys and its own stores;
- the adapter brings typed calls, events in through `on:`, a stand-in for worlds, and a conformance test;
- the portal shows an origin badge on every thing and operation that came from a plugin.

Acme mounts the model, the api, the server (M1.11), the sdk, the cli and the mcp (M1.12), one file each in
`blueprint/projections/`, and what a mount makes is what is written: take `server.ts` away and `generated/server/` is
gone. A project that mounts no projection, signup included, gets those six as if it had. What is still a fixed list in
the generator, for every project, is the rest:

```ts file=packages/generators/src/modules/render/service.ts name=imports,imports lines=1-6
import { Effect } from "effect";
import { emptyServer, renderHandlerScaffold } from "@orthograph/projections/shared";
import { PortalRender } from "#modules/portal/service.js";
import type { RenderApi } from "./types.ts";
import { renderDocs } from "./internal/docs.ts";

```

The docs and the portal become projections the blueprint mounts when M1.13 lands.

## How it works

1. **A mount is a file, named by its path.** It lives in one of three folders, one per kind:
   `blueprint/features/<name>.ts`, `blueprint/adapters/<name>.ts`, `blueprint/projections/<name>.ts`. The mount's
   name is its file's name, never a string (M1.06).
2. **The plugin stays in its package.** Its declarations, handlers and journeys are pinned to one version and never
   copied in. Compile folds them into the model under the mount's name, each carrying where it came from (M1.06).
3. **The four verbs shape it** (M1.07):

   | Verb | What it does | Used by |
   |---|---|---|
   | **choose** | picks one of the options the plugin proved, such as a signer or a CLI's command name | features, adapters, projections |
   | **include** | names which of an adapter's calls and events are reachable | adapters |
   | **narrow** | removes ways in or operations | features, projections |
   | **omit** | drops an operation; `check` fails if anything of the app's calls it | features |

   Each one only takes away or picks among proved options. None can widen what the plugin does, so a journey that
   passed in the plugin's CI still passes in the app, or is skipped and named.
4. **A plugin names what it needs, and mounting finds it** (M1.08). A need is never met by a copy inside the plugin,
   so an app has one auth and one browser wallet however many features use them:

```ts planned=M1.08 path=@orthograph/wallets/blueprint/feature.ts
export default Blueprint.feature({
  needs: [auth, Blueprint.need(eip1193, { when: signer.browser.injected })], // eip1193 only with a browser signer
});
```

5. **`check` names every clash.** Two things with one name, an unmet need, an omitted operation still called, or a
   narrowing that would empty an operation: each is an error naming both files (M1.08).
6. **Each plugin brings runtime entries per host** (`worker`, `node`), and only the right ones reach a Worker (M1.09).
   A plugin never chooses its host ([languages and hosts](languages-and-hosts.mdx)).
7. **`ortho add` writes the mount** (M1.10). It pins the package exactly, refuses a version under three days old, writes
   the mount with the plugin's default choices, and offers to meet its needs.

## Choices

**A choice or a setting?** A **choice** is part of what the system is, and it never varies by environment: on-chain
voting, a browser signer. A **setting** is a value that must differ between environments, such as which chains a
wallet links for. The plugin declares it and each environment gives it:

```ts planned=M1.07 path=blueprint/environments/production.ts
settings: [wallets.settings.chains.is([1, 8453])],
```

**Narrow or omit?** Narrow keeps an operation but takes ways in away from it. Omit drops the operation:

```ts planned=M1.07 path=blueprint/features/wallets.ts
export default Blueprint.use(wallets, (w) => [
  w.signer.browser.injected,                                        // choose: a signer wallets has proved
  w.narrow(w.operations.list, { via: [w.via.session, w.via.device] }), // narrow: fewer ways in
  w.omit(w.operations.import),                                      // omit: acme doesn't import keys
]);
```

**Mount a plugin twice?** Name the second mount's file differently. If a mount's name matches the plugin's own, its
things keep their names; if it differs (`usdc.ts` for an ERC-20 plugin), they are prefixed with it (`usdc-token`).

**The app needs an operation to behave differently?** Write your own operation over what the feature exports. There
is no override.

## What it is not

- **Not a copy.** A mount puts one file in your project. The plugin's code stays in its package and is upgraded by
  version, not edited.
- **Not an override.** A mount can choose, include, narrow and omit. It can never widen or rewrite.
- **Not a language or a host.** A language is what behaviour is written in, and a host is where it runs
  ([languages and hosts](languages-and-hosts.mdx)). A plugin is a piece of a blueprint; it runs wherever the app does.
- **Not an environment.** A mount says what the system is, once. An environment gives settings per place
  ([environments](environments.mdx)).
