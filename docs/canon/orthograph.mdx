## The idea

Orthograph is a framework for building a whole system with an agent. You and your agent describe the system once, as
typed declarations: the things it holds, the operations on them, who may call each one, how each can fail, and what
must always be true. Orthograph makes everything else from that description, and makes it again whenever the
description changes.

It is built for the agent doing the work. An agent loses its way when a system is scattered across files it can't see
at once, and when nothing checks what it says it did. A [blueprint](blueprint.mdx) is one small typed declaration per
file, so the whole system fits in view. `ortho check` refuses a description that doesn't hold together. `ortho prove`
runs stories through the real system, so done is a verdict, not a claim. A person reads the same files, and watches
the running system in the [portal](portal.mdx).

Two rules decide the rest. **Each operation is enforced in exactly one place**, and every way in reaches that place,
so a refusal is the same from a screen, the command line, an agent's tool or another service. **Behaviour is the only
freehand**: what an operation does is a [handler](handlers.mdx) you write, and everything around it is generated and
stays generated. Each thing Orthograph makes is a **projection**: one view of the same model, made by code, never by
hand. **The loop** is how a change moves: describe, compile, generate, write the behaviour, prove, ship, watch, and
whatever is missing or red comes back as the next piece of work.

## The smallest example

Plugged In is the app the canon is built around (K9); 1.0 is the framework Capxul core proves (K42, K43). In its first stage a person claims a name and gets a public page of links.
This is the whole of claiming a name:

```ts file=examples/plugged-in/blueprint/things/handle/verbs/claim.ts name=default lines=7-16
export default Blueprint.operation(Handle, {
  description: "Claim a free name and make it the address of your public page, with its profile.",
  payload: { name: Handle.fields.name },
  answer: { handle: Handle.fields.id },
  move: machine.moves.claim,
  allowed: [Blueprint.signedIn],
  steps: { record: Blueprint.step.database({ writes: [Profile] }) },
  idempotent: "request", // the same request twice claims once
  budget: { p95: "150 millis" },
});
```

Its two refusals, a name someone else holds and a person who already has one, aren't written here. They come from
the handle's rules ([invariants](invariants.mdx)), and the runtime refuses them before anything is committed.

Everything below is made from those ten lines. "Runs" means it is generated and running today; the rest is decided
for 1.0, and names the slice that builds it.

What runs is in `examples/plugged-in/generated/`, one folder per projection: `api`, `server`, `sdk`, `cli`, `mcp`,
`docs`, `portal`, `infra` and `model`. The served operation is `examples/plugged-in/generated/server/main.ts:37`.

None of those ways in checks anything on its own. Each one reaches the served operation, which decides.

This is the only part of claiming a name that someone wrote. Orthograph scaffolded it once, with a header saying
everything the runtime already does, so the handler doesn't; from then on it is yours:

```ts file=examples/plugged-in/src/handle/claim.ts name=claim lines=42-63
const claim: Handler = ({ name }, { principal, steps, move, id }) =>
  Effect.gen(function* () {
    // `signedIn` admits a person and an agent acting for one (M2-auth, fork 2): the page is the person's either way.
    const who = acting(principal);
    if (!who) return yield* Effect.die(new Error("reached without a signed-in person"));
    const records = yield* Records;

    // HandleTaken and HandleAlreadyOwned are the rules' (invariants.ts): the runtime refuses them after the move, before the commit.
    // Step record: database, span handle.claim.record. The handle and its public page are made together.
    const profile = yield* Ids.of(Profile.fields.id);
    yield* steps.record(
      Effect.gen(function* () {
        yield* records.insert(Handle, { id, name, owner: who.person as never });
        yield* records.insert(Profile, { id: profile, handle: id, links: [] });
      }),
    );

    // The move claim, to claimed.
    yield* move();

    return { handle: id };
  });
```

It saves the handle and its page. It never decides who may call, never parses a request, never names a route and
never refuses a taken name. The declaration already said all of that.

And this is how anyone knows it works: a story, written by a different agent before the handler existed, run
against the real system in a world of its own.

## How it works

A change moves through seven steps. Each has its own page.

1. **Describe.** You and your agent write declarations under `blueprint/`, and mount plugins into it
   ([blueprint](blueprint.mdx), [plugins](plugins.mdx)). Built.
2. **Compile.** `ortho check` compiles the blueprint to the model: one JSON file, every declaration hashed. Every
   projection is made from the model, never from the blueprint directly. Built.
3. **Generate.** The projections write `generated/`. A generated file that differs from what the model renders fails
   `ortho check`, so nobody can edit one and keep it ([projections](projections.mdx)). Built.
4. **Write the behaviour.** Each operation's handler is scaffolded once and never overwritten
   ([handlers](handlers.mdx)). Built.
5. **Prove.** `ortho prove` runs the stories in a world with real stores, the evals judge what they left behind, and
   a verdict is recorded ([journeys](journeys.mdx), [proof](proof.mdx)). Built.
6. **Ship.** `ortho promote` moves one exact build from environment to environment, and `ortho env destroy` leaves
   nothing behind ([environments](environments.mdx)). Built on this machine; the first live staging run is M7.04, and the release M7.13.
7. **Watch, and close the loop.** The portal shows the running system under the model's names, and the
   [factory](factory.mdx) turns missing parts, red verdicts and drift into tasks that only a fact can close. The
   factory comes after 1.0 (M3.09); until then you read what `ortho check` and `ortho prove` say, and act on it.

Where each operation runs is the language's and host's business ([languages-and-hosts](languages-and-hosts.mdx)): an
operation written in Effect is enforced by a wrapper on a Cloudflare Worker, and one on a chain by its contract (K7).
Where its data lives is [data](data.mdx). Every way in, and why none holds authority, is [doors](doors.mdx).

What flows down that line is the description; what flows back up is evidence. Four kinds come back. **Drift**:
`ortho check` fails when a generated file differs from what the model renders. **Evidence**: every call leaves spans,
events and refusals named from the model, and journeys assert on them. **Staleness**: a full prove records what each
passing operation rested on, so `ortho impact` names what a change made stale and `ortho prove --changed` reruns only
that. **The scaffold growing**: `ortho check` warns when a declared refusal, state or step has no place in a handler
you already wrote.

## How to think in it

Merged here from the model draft of 20 and 21 November 2026 by K41; the draft, with a file and line for every claim,
is kept as a record in `design/history/retired-2026-11-23/model/README.md`, and its five calls are K30's.

**The ideas you think in.** A [thing](things.mdx) is a noun with an id and fields; a value is a named field type that
says what it is in every language. A [machine](machines.mdx) holds a thing's states and moves, and refuses a move
from the wrong state for you. An [operation](operations.mdx) is a verb on a thing: payload, answer, refusals, move,
who may call, steps and budget; a read changes nothing and has no handler. A refusal is a declared error with a stable
code; an event is what a move records. A role says who may call; a rule ([invariants](invariants.mdx)) says what must
hold across records, and owns its refusal. A [journey](journeys.mdx) is a story through real operations that is the
spec; a starting world is a setup made only by running operations; an [environment](environments.mdx) says where the
app runs; a mount says "use this plugin here, like this" ([plugins](plugins.mdx)).

**Five habits.**

1. **Declare what you know**, and nothing you don't know yet.
2. **Leave blanks for the agent.** A gap is `Blueprint.todo("what goes here")`: it compiles, and `ortho check` names
   every one until it is filled.
3. **Journeys are the spec.** A different agent from the builder writes them, and they fail on empty handlers before
   anyone builds. Building is climbing: prove, fix the handler, prove again, until every journey is green.
4. **The grid is the guardrail.** Every building block in every output is an eval (K14). The climb proves the app
   works; the grid proves every output carries every block.
5. **Outputs fall out.** You never write the SDK, the CLI, MCP or the docs; a change to the blueprint changes them all.

**Three loops.**

- **Ideation, from an idea to a demo.** Name the idea in one sentence ("claim `@name`; a public page of links").
  `ortho add thing` and `ortho add operation` declare the things and verbs, each gap a blank; fill in the machine and
  the rules you know; `ortho add journeys` writes a stub for every path through the machine, every role, and every
  refusal an operation declares or a rule can give it, and a journey author fills them in or deletes the ones that
  cannot happen. Then check, generate, prove and climb, and look at it in the portal.
  K30 makes `ortho add thing` take the states and verbs you already know, so it writes blanks only for the rest.
- **Development: edit, check, prove, see what's stale.** Edit a handler or a declaration; `ortho generate` re-renders
  and scaffolds anything new; `ortho check` finds blanks, types, rules and drift; `ortho prove` runs every journey in a
  world, or `--only` one, or `--changed`; `ortho impact` says what the change made stale; the portal shows the calls.
- **Extraction, from app code to a plugin.** Build a thing once inside an app, climb it green, then extract it (K30):
  find the seam, make the package with `ortho new feature` (M2.10), move the declarations, handlers and journeys in
  unchanged, write its one-file descriptor, prove it alone, publish it, mount it with one file, and delete the copy.
  The first candidates are the starter's people and organisations (`@orthograph/auth`, `@orthograph/organizations`,
  M2.05 and M2.07) and Plugged In's handle (`@orthograph/handles`, ST1.03). Mounting is built; the loop has never run
  end to end.

Where each part stands, release by release, and how the packages divide into the core and the standard library, is
the canon's status page, [`status.md`](status.md).

## Choices

**Declaration or handler?** Put it in the declaration whenever the declaration can say it. What a declaration says is
generated into every way in, enforced in one place, checked, traced and documented. What a handler does is only in
that handler.

| You want to say | Say it in | Because |
|---|---|---|
| who may call | the operation's `allowed` | the enforcer refuses before the handler runs, whichever way the call came in |
| a state it must be in | the machine's move | the refusal is generated |
| something true across many records | a rule ([invariants](invariants.mdx)) | the runtime refuses a break before anything is committed |
| a way it can fail | the operation's `errors` | it gets a code, an exit code, a typed error in the SDK and a line in the docs |
| how it decides and what it writes | the handler | only behaviour is freehand |

**Generated client or your own?** Use the generated SDK, CLI, MCP tools and actions. Each is remade when the
blueprint changes, and each reaches the same enforcer. A client written by hand drifts the day an operation changes.

## What it is not

- **Not a one-off code generator.** Generated files are never yours. They are remade from the model, and editing one
  fails `ortho check`. Only scaffolds become yours ([handlers](handlers.mdx)).
- **Not low-code.** A handler is ordinary Effect code. Orthograph takes away the code around behaviour, not behaviour.
- **Not the blueprint.** Orthograph is the framework and its command. The [blueprint](blueprint.mdx) is what you
  write with it.
- **Not a host.** Orthograph makes what runs; a host such as Cloudflare or a chain runs it
  ([languages-and-hosts](languages-and-hosts.mdx)).
- **Not an agent-native app.** Orthograph ports what it needs from agent-native into its own code and keeps its
  action field names; nothing of agent-native runs (K5). The details are on [doors](doors.mdx) and [ui](ui.mdx).
