## The idea

A machine is a thing's states and the moves between them. A move names the states it may start from, the states it
may end in, and the event it emits. An operation makes at most one move, and says which. One rule decides it: **a
thing's state changes only through a declared move, and every move writes its event in the same commit as the new
state.** A call from a state the move can't start from is refused before your handler runs, with a refusal the
machine makes for you.

## The smallest example

The sign-up sheet has three states and three moves:

```ts file=examples/signup/blueprint/things/sheet/machine.ts name=machine lines=5-13
export const machine = Blueprint.machine(Sheet, {
  states: ["open", "full", "closed"],
  moves: {
    open: { from: [], to: "open", emits: Events.SheetOpened },
    join: { from: ["open"], to: ["open", "full"], emits: Events.PlaceTaken }, // the last place fills it
    close: { from: ["open", "full"], to: "closed", emits: Events.SheetClosed },
  },
  notFrom: { exit: 70 }, // generates SheetNotOpen
});
```

`join` has two outcomes: the sheet stays `open`, or the last place fills it. Each move emits an event, declared beside
it in `examples/signup/blueprint/things/sheet/events.ts`. An event is named by its export:

```ts file=examples/signup/blueprint/things/sheet/events.ts name=SheetOpened,SheetClosed lines=5-7
export const SheetOpened = Blueprint.event({ sheet: Sheet.fields.id, places: Count });
export const PlaceTaken = Blueprint.event({ sheet: Sheet.fields.id, left: Count });
export const SheetClosed = Blueprint.event({ sheet: Sheet.fields.id });
```

The compiled model draws the machine, and the refusal it made: `SheetNotOpen`, code `SH-900`, exit 70.

An operation says which move it makes. `sheet.join` makes `join`:

```ts file=examples/signup/blueprint/things/sheet/verbs/join.ts name=default lines=11
move: machine.moves.join,
```

## How it works

A move happens in three places in one call: a check before the handler, a choice inside it, and the state and event
in the commit after it.

### Before the handler: the wrong-state check

Once the caller has passed the role check, the machine checks the state
(`packages/language-effect/src/modules/handler/service.ts:90`):

```ts file=packages/language-effect/src/modules/handler/internal/move.ts name=checkFrom lines=30-37
 */
export const checkFrom = (op: Operation, refusal: string | undefined, subject: Instance | undefined) =>
  Effect.gen(function* () {
    const move = op.move;
    if (!move || move.from.length === 0 || refusal === undefined || subject === undefined) return undefined;
    const state = subject.state ?? "none";
    if (!move.from.includes(state)) return yield* Effect.fail(new NotFrom({ _tag: refusal, state }));
    return state;
```

- A move with `from: []` creates the thing, so there is nothing to check. That is `open`.
- The instance is the payload's field declared as the thing's own id: `join`'s `sheet: Sheet.fields.id`
  (`packages/language-effect/src/modules/handler/internal/move.ts:14`), read once before the handler and handed in as
  `subject`. If it isn't found, the runtime has already refused the call (K16): `<Thing>NotFound`, or `NotAllowed` when a
  role check reads that field, so a stranger learns nothing about what exists.
- If the state isn't one the move starts from, the call fails with the machine's refusal, carrying the state it
  found. The handler never runs, and nothing is written.

That refusal is generated, never written. The compiler names it after the thing and its first state, gives it the
number 900 so adding an error never moves it, and takes the exit you gave (`notFrom: { exit: 70 }`). Over HTTP it is a
409 (`examples/signup/generated/api/src/errors.ts:8`). A journey names it as `machine.notFrom`, with the state it
expects. Once both places are taken, the sheet is full, and a third join is refused by the machine:

<Scenario journey="examples/signup/journeys/fill-a-sheet.ts" step="a third join is refused: a full sheet is not open" />

The same refusal covers every move that starts from the wrong state. A closed sheet refuses a join, and refuses a
second close too, though `close` may start from `full` as well as `open`. That name is the note `refusal-name`:

<Scenario journey="examples/signup/journeys/a-closed-sheet-takes-no-one.ts" step="closing it again is refused" />

Reading the instance here also fixes the version the commit is guarded by. So if a close lands between this check and
a join's commit, the join's commit is a conflict and runs again, and then the check refuses it. How the version guard
works is on [stores](stores.mdx).

### Inside the handler: choosing the outcome

The handler gets `move` and calls it once, with the state it ends in. A move with one `to` may be called with
nothing, or its one state, as `close` does (`examples/signup/src/sheet/close.ts:8`). A move with several must be told
which. This is the sheet's join:

```ts file=examples/signup/src/sheet/join.ts name=join lines=22-24
yield* steps.record(records.update(Sheet, sheet, { taken: taken + people }));
yield* move(people === left ? "full" : "open");
return { left: left - people };
```

An outcome the move doesn't declare dies as the handler's bug. The span says what was asked first, as `move.to`, so
the wrong outcome is evidence too (`packages/language-effect/src/modules/handler/internal/move.ts:48`). A handler that
refuses never calls `move`, so nothing moves. When two people ask for the one place left, the handler refuses with
`SheetFull`, a refusal of its own, and the sheet stays open:

<Scenario journey="examples/signup/journeys/fill-a-sheet.ts" step="two people are refused: only one place is left" />

What a handler gets and returns is [handlers](handlers.mdx).

### After the answer: the state and the event, in one commit

Once the handler has answered and its answer is checked, the move is applied
(`packages/language-effect/src/modules/handler/internal/move.ts:56`). The event's fields are taken from the instance
as this call left it, then the payload, then the answer. A field found in none of them dies. `PlaceTaken`'s `left` is
in the answer. Then:

```ts file=packages/language-effect/src/modules/handler/internal/move.ts name=applyMove lines=79-83
// The journal is a record anyone who reads it can see: a secret or private field of the event is not written to it.
const fields = Object.fromEntries(Object.entries(encoded).filter(([k]) => journalled(move.emits.fields, k)));
yield* unit.setState(op.thing, subject, outcome);
const trace = yield* Effect.currentSpan.pipe(Effect.map((s) => s.traceId), Effect.orElseSucceed(() => ""));
return { trace, operation: name, move: move.key, subject, event, fields } satisfies Entry;
```

The new state goes into this call's writes, and the event becomes a journal entry. Both go into the one commit with
the handler's own writes (`packages/language-effect/src/modules/handler/service.ts:71`). So the state and its event
land together or not at all. A handler that dies after writing leaves nothing behind
(`packages/language-effect/src/modules/handler/handler.test.ts:267`). The commit itself is [stores](stores.mdx).

The state is kept beside the thing's fields, not as one of them. In D1 it is a `state` column, empty until the first
move sets it (`packages/projections/src/modules/server/internal/worker-config.ts:64`).

### What an event is for

An event is the record of a move: what happened, to which instance, in which call. Today it is used in three ways:

- **The journal.** Every entry names the call's trace, the operation, the move, the instance and the event's public
  fields (`packages/language-effect/src/modules/journal/types.ts:4`). It is the system's own history, written with the
  state it explains.
- **Proof.** `ortho prove` finds a step's events by its trace. That is how a journey checks a move happened, with
  `emits(PlaceTaken, …)`, or that nothing moved, with `noEvents()`.
- **The trace.** The operation's span carries `move.name`, `move.from` and `move.to`, and the commit span `event.name`. See [traces](traces.mdx).

Here a journey checks both the event and the state the move left, when the last place fills the sheet:

<Scenario journey="examples/signup/journeys/fill-a-sheet.ts" step="the second join takes the last place and the sheet is full" />

Two more are designed. The outbox delivers every move's event at least once, to whatever listens (M5.04). And a view
is a list kept from events, so it can list things across stores and actors (M5.05, on [views](views.mdx)).

### Events without a move

Today an event comes only from a move: no machine, no event. That leaves an operation that writes but has no state to
change, such as editing a draft's text, with nothing in the journal. K5 settles it (Q5): an operation may declare
`emits:` of its own, and its event is committed with the call's writes, only when the call succeeds and only when it
wrote something. That is built in M3.16, and it is declared on the operation, so it is on
[operations](operations.mdx), not here:

```ts planned=M3.16 path=blueprint/things/draft/verbs/edit.ts
export default Blueprint.operation(Draft, {
  description: "Change a draft's text.",
  payload: { draft: Draft.fields.id, text: Body },
  answer: {},
  emits: Events.DraftEdited,
  steps: { record: Blueprint.step.database() },
});
```

### The four places a refusal comes from

The machine's refusal is one of four places a call can be refused, in the order a call meets them
(`packages/language-effect/src/modules/handler/service.ts:112`):

1. **The runtime's own checks**, first: who may call, whether the instance exists, a request key reused.
2. **The machine**, before the handler: the instance is in a state the move can't start from.
3. **The handler**, a declared error only it can know, like `SheetFull`.
4. **A rule**, after the handler answers and the move is made, before the commit.

The last two are the ones a machine's state can't decide. The declared `states` array also becomes a record of
references, so a rule can name one:
Plugged In's `oneHolderPerName` holds `while: [machine.states.claimed]`, and a rule sees the state the move just set. All
four are on [operations](operations.mdx), and the rule is on [invariants](invariants.mdx).

### Why a machine, and not a status field

A status field is a value any handler can set to anything. A machine makes four things true that a field can't:

- **Only declared moves.** `close` can't start from `closed`, and `join` can't end in `closed`. The runtime checks
  `from` before the handler and `to` after it, so a handler can't move the thing anywhere the machine doesn't allow.
- **One refusal, made for you.** A call from the wrong state is refused the same way at every door: the same name,
  the same code, the same exit, and a journey can name it. With a status field, each handler writes its own check, or
  forgets to.
- **Every change leaves an event.** A move writes its event in the same commit as the state. Setting a field leaves
  nothing to prove from, and nothing a view can be kept from.
- **The model can draw it.** States and moves are in the model, so the docs and the portal show the machine as a
  diagram, not a column.

## Choices

### One outcome, or several

Give `to` one state when the move always ends there: `close` always ends `closed`. Give a list when the handler
decides from the data: `join` ends `open` or `full`, depending on how many places are left. The handler must then say
which, and a wrong one dies.

### Where a move may start

`from: []` makes a move that creates the thing, like `open`. Otherwise list every state it may start from. A state you
leave out is refused by the machine, before any of your code runs.

### Which fields an event carries

Put in an event what a reader of the journal needs to know what happened: the instance's id, and the facts of the
move. `PlaceTaken` carries the sheet and how many places are left. Only public fields are written, so a secret or
private field in an event is dropped from the journal (see [things](things.mdx)). Fields a call doesn't have die, so
each one must come from the instance, the payload or the answer.

### A machine, or none

A thing whose life has stages gets a machine: a sheet, an invitation, an organisation. A thing that is only kept and
changed, like a person, needs none. Its operations declare no `move` and, until M3.16, emit no events.

## What it is not

- **Not a field.** The state is not one of the thing's fields, and a handler doesn't write it. See [things](things.mdx).
- **Not a data refusal.** `SheetFull` depends on how many people ask, so it is declared in `errors.ts` and raised by
  the handler. The machine's refusal depends only on the state.
- **Not a rule.** A refusal comes from one of four places: the handler, the machine, the runtime's own checks and the
  thing's rules, all listed on [operations](operations.mdx). The machine is the one that knows a single record's state,
  and refuses before your code runs. A rule is the one that knows many records, such as one holder per name, and refuses
  after the move, before the commit. It reads the state the move just set, which is why `claimed` is a state a rule can
  name. See [invariants](invariants.mdx).
- **Not a role check.** `NotAllowed` says who may call, and it comes first. Everyone may call the sheet's operations
  (`Blueprint.anyone`), so signup never shows it: see [roles](roles.mdx).
- **Not a workflow.** A machine doesn't wait or run on its own. Every move is one call. Work that waits is
  [workflows](workflows.mdx).
- **Not a view.** An event is one move's record. A list built from many events is a view: see [views](views.mdx).

## Notes

<Note kind="decision" decision="D2">
  A handler makes its move with `move(to?)`, and the wrapper applies it after the answer (#25). The outcome is written
  on the span before it is checked, so an undeclared one dies and is still evidence.
</Note>

<Note kind="decision" decision="D3">
  Refusal codes are stable across languages, and the machine's own refusal is always 900 (`SH-900`), so adding an
  error never moves it.
</Note>

<Note kind="decision" decision="K5">
  Q5: `emits:` on an operation with no machine, committed with the call's writes, only on success and only when the
  call wrote. Built in M3.16, owned by [operations](operations.mdx).
</Note>

<Note kind="status" slice="M5.04">
  Today an event reaches the journal and nothing else. Nothing listens to it yet.
</Note>

<Note kind="status">
  D2 #25 says an event's fields come from the answer, then the payload. The code also reads the instance as the call
  left it (`packages/language-effect/src/modules/handler/internal/move.ts:62`), so an event can carry a fact of the
  instance that is in neither the payload nor the answer. This page follows the code.
</Note>

<Note kind="question" id="refusal-name">
  Ledger `MAC-02`. The machine has one refusal, named after its first state
  (`packages/compiler/src/modules/model/internal/describe.ts:72`). So closing a closed sheet is refused as
  `SheetNotOpen`, though `close` may also start from `full`. The comment on the type says `<Thing>Not<State>`
  (`packages/orthograph/src/modules/machines/types.ts:23`), which reads as if the name followed the move. Should the name
  say what is wrong for every move, such as a refusal per move, or one neutral name? Renaming it is a major change
  once released, since clients match on the name.
</Note>

<Note kind="question" id="move-not-made">
  An operation that declares a move, and whose handler answers without calling `move`, commits with no new state and
  no event. Nothing refuses it. For a move with one outcome, should the runtime make the move when the handler
  answers? Or should a handler that answers without moving die, as an undeclared outcome does? No ledger row owns it
  yet.
</Note>

<Note kind="decision" decision="K16">
  A move on an instance that doesn't exist is refused before the handler (M1.46). The runtime reads each thing the
  payload names by id; a missing one is `<Thing>NotFound` (`SH-901`, exit 4, HTTP 404), generated beside `SheetNotOpen`,
  or the thing's own declared error of that name. When every way in is a role check that reads it, the miss stays
  `NotAllowed`, so a stranger learns nothing about what exists. A join on a sheet that was never opened is now a refusal
  the caller can name, not a defect. Ledger: MAC-07.
</Note>
