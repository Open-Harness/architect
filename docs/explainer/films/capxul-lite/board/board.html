The next step

The problem it solves

Ada presses one button: Spend. Underneath, that is two operations in two places, with her wallet between them.

  • spend.draft runs on our server. It records who is being paid and why. Ada is a signed-in person.
  • budget.spend runs on the chain. It moves the money. Ada is an account, and her wallet signs.

Everything Orthograph makes, it makes per operation. So on its own you get two SDK methods, two commands, two agent tools and two buttons, and nothing that says they belong together.

Every client then has to know the recipe. Draft. Take the id. Fill in the chain call. Try it. Ask the wallet. Send it. That recipe ends up written by hand in the app, in a script, and in the agent's prompt. That is the exact duplication the framework is for removing. And an agent that skips the draft moves money with no reason attached.

The idea

Say it once, on the first operation: what the same caller does next, and which fields are carried across.

It is a fact about two operations, held in the model. So everything made from the model can use it.

What it is not

  • It enforces nothing. It is a promise about the clients we generate. The contract can still be called directly from any wallet. That is why "unexplained" is a real state.
  • It is the same caller, straight away. A different person acting later, like an owner approving a grant, is not a next step. That is the thing offering a move to whoever holds the role.
  • It is not new to the repo's thinking. K5 sketched a "client" activity for exactly this. The workflows decision, M3.01, dropped it: the person calls the operation themselves. That is fine for the engine. It leaves every client guessing, which is the gap this fills.

Still open on it

  • Can there be a choice of next steps, or only one?
  • Can a next step have its own next step, three in a row?
  • Should a note be forced? The only way is for our server to co-sign every payment. Then nobody can spend while our server is down, which gives away the reason the limit is on chain.

Is a spend a workflow?

No. It is a machine, and it should stay one.

The test I used: does anything have to remember where the work has got to, other than the thing itself? For a spend, no. Drafted, sent, paid and unexplained are the spend's own states. The accountant sees them. Each step is one move on one thing, in one commit. What joins the steps is an event, a clock, or Ada.

I owe you one correction on the repo's own wording. Its data page says work that changes a store and a chain "is a workflow, with a waiting state between". That sentence uses the word loosely. The repo also has a real workflow primitive, decided in M3.01 and not built: a long-running handler that calls operations and waits for events and dates. A spend does not need one. I would tighten that sentence.

Why not write it as a workflow anyway

  • The order would move into code. A workflow declares its activities, but the order and the branches live in its handler. That is the layer you should not have to read.
  • A machine is data. So it can be checked for a state with no way out, drawn as the sequence above, and turned into the strip under the button.
  • It needs no new engine. Events arrive through the outbox and the indexer. Time arrives through the keeper.

When a workflow is the right word

When the progress belongs to no single thing. Paying forty people in one payroll run. Collecting signatures off chain from a changing set of owners. A loop, or a fan-out, with something to undo if it fails halfway.

Events, errors and the indexer

An event

Every move records one. It is written in the same commit as the change. On chain it is a Solidity event, with who signed and their nonce added in front. Events are the only thing that crosses from one place to another.

An error

Declared once, and named on the operation or the rule that can raise it. It gets one code, kept in a lock file that only ever grows. So "budget exceeded" is the same name and the same code from the contract, the API, the SDK, the command line, an agent's tool and the app.

The indexer

  • One per contract, per environment. It is an actor.
  • It knows the events from the model. Nobody hands it an interface file. It turns raw logs back into the events you declared.
  • It keeps its place, waits as many blocks as the environment says, and hands on only what the chain will keep. If a confirmed event is undone later, it hands on a correction.
  • It feeds four things: operations started by an event, anything waiting on one, the list of budgets, because a contract has no list, and the portal and traces.

What exists

  • The environment file, with local, test and staging.
  • The server's infrastructure as generated code, and one command to bring staging up and take it down.
  • The server's bundle is built once per revision and deployed unchanged.
  • Decided, not built: an environment binds a chain store to a network. One deployment per network, not one per company.

What I could not find decided

  • Who deploys the contract, and where its address is kept. I would keep it in a checked-in record that only grows, like the refusals lock.
  • Production as an environment. It appears only in a portal brief, as "promotes from staging". A server can be promoted. A contract can't. It can only be deployed again from the same revision, and checked.
  • The order of bringing it up. Contract, then the indexer from the contract's first block, then a funded relayer, then the server.
  • Taking it down. The server and database are destroyed. A staging contract is left behind on its test network for good.
  • The relayer's gas. Who funds it, and who is told when it runs low.

Seven decisions for you

  1. A spend is a machine, not a workflow. Agreed?I would also tighten the repo's sentence that calls any work across two places a workflow.
  2. Keep the next step as one line on the operation?It is the smallest thing that makes one button out of two operations for every client at once.
  3. Which private chain do you mean?A permissioned network running the same contracts, or a privacy chain like Aztec with private notes. The first is nearly free. The second is another language.
  4. One contract for every company, or one per company?K25 says one per network. You asked for "one contract that is a multi-sig with budgets". If a company needs its own address, the blueprint needs a factory.
  5. Is the reference per thing what you mean by hooks and headless components?K29 says pieces, not hooks. I think both are wanted: a piece per operation, a reference per thing.
  6. Changing a live contract: upgrade in place, or deploy new and move?This decides what the "change" part of the film can honestly claim.
  7. Shall I ask the framework goal to record "indexer"?It is their name to change. I should not sweep 113 files from this session.

After that, the recut: four places a thing can live, who is who, events and errors, each output shown, the spend as a sequence, the journey run on screen, and the four environments. That is longer than eight minutes. It may be better as two films.
