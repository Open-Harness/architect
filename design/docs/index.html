Framework manual · Orthograph · orthograph

Describe it once. Everything else is made from it.

Orthograph turns one description of a system into its server, clients, docs, tests, deploys and the tools its agents build with. The only code anyone writes by hand is behaviour, and every piece of it is judged against the description.

Built today runs on main nowPlanned · M2 designed and decided, landing in that milestone
Chapter 1

Start

Orthograph in one breath

Design decided · K2

You write one description of a system: what exists, how it changes, who may change it, what is recorded, and what must hold. Orthograph compiles it into a model. Every output is a projection of that model. Behaviour, inside generated frames, is the only freehand. Everything that runs is judged against the description by the same names.

One description

Things, machines, operations, roles, events and journeys in blueprint/. Compiled, it is the model: one contract, every name written once.

Many projections

The server is the model on a host. The SDK, CLI and MCP are the model for callers. Docs and the portal are the model for readers.

Behaviour is the only freehand

Handlers fill blanks in generated frames. Their types come from the declaration, so a handler can't return what the operation didn't declare.

Facts, not claims

Journeys run in real worlds, evals judge the evidence, and CI writes signed verdicts. Only a verdict says an operation works.

Names. The framework is Orthograph, and its command is ortho. Packages live under @orthograph/*, and orthograph is the one you install. Blueprint is what you write: the blueprint/ folder and the Blueprint.* API.

The loop

Parts built · loop closes at M3

Everything in Orthograph sits on one loop. You plan, the description compiles, checks come first, the factory fills the blanks, worlds prove it, environments ship it, and what production records comes back as new work.

  description: "Money a member may spend from their organisation, up to a limit each month.",
  fields: {
    id: Blueprint.id("alw"),

  states: ["active", "exhausted", "revoked"],

    grant:  { from: [], to: "active", emits: Events.AllowanceGranted },
    spend:  { from: ["active"], to: ["active", "exhausted"], emits: Events.AllowanceSpent },
    revoke: { from: ["active", "exhausted"], to: "revoked", emits: Events.AllowanceRevoked },

});

blueprint/things/allowance/verbs/spend.tsexport default Blueprint.operation(Allowance, {

  move: machine.moves.spend,
  errors: [AllowanceExceeded],
  allowed: [grantee],
  steps: { load: Blueprint.step.database(), record: Blueprint.step.database() },
  idempotent: "request",            // retried with the same request key, it spends once
  budget: { p95: "150 millis" },
});

Chapter 2

Concepts

The description

Built today

A description is a set of files under blueprint/. Each file declares one thing, and its name comes from its path. Nobody writes a declared name as a string.

DeclarationWhat it saysWhere
thinga noun with an id, fields, and a home for its state (lives)things/<thing>/thing.ts
valuea named field type, meaningful in every language (Amount is a bigint in Effect, a uint128 in Solidity)values/
machinea thing's states and moves. Refusals for a wrong state are generatedmachine.ts
operationa verb: payload, answer, errors, move, allowed, steps, budgetverbs/<verb>.ts
readan operation that changes nothing and has no handlerverbs/
rolewho may call: a rule over the thing, a built-in (anyone, signedIn), or a service roleroles.ts
eventwhat a move emits, named <Thing><PastTense>events.ts
errora declared refusal, with an exit code and a stable refusal code ([AL-002])errors.ts
stepa named span inside an operation: a database write, a call, a use of a feature's export, a waiton the operation
budgethow fast it must be (p95), judged in every world and in productionon the operation
blueprint/things/allowance/errors.tsexport class AllowanceExceeded extends Blueprint.error("AllowanceExceeded", {
  exit: 41,
  carries: { remaining: Amount },
  explains: "The spend is more than what is left this month.",
}) {}
Today. All of this compiles on main (examples/acme/blueprint/things/allowance/). lives: "chain" is planned for M6.

Journeys and starting worlds

Executable built · stories M1

A journey is a short story through real operations, played by a cast and starting from a named world. It is written first as prose, while you plan. A different agent from the builder then turns it into steps. That rule keeps checks honest: whoever fills a handler never wrote the test it must pass.

blueprint/journeys/revoke-then-spend.ts · executable; the builder never edits itexport default Blueprint.journey("revoke then spend", {
  cast: { ada: owner, olga: grantee },
  starts: funded,
  steps: (s) => [
    s.step("ada revokes it",
      s.ada.run(revoke, { allowance: s.world.allowance }),
      emits(AllowanceRevoked, { allowance: s.world.allowance }),
      machine.isIn(s.world.allowance, "revoked")),
    s.step("olga can't spend",
      s.olga.run(spend, { allowance: s.world.allowance, amount: 1n, memo: "coffee" }),
      refuses(machine.notFrom, { state: "revoked" }),
      noEvents()),
    s.step("olga can't revoke it either",
      s.olga.run(revoke, { allowance: s.world.allowance }),
      refuses(Blueprint.NotAllowed)),
  ],
});

A starting world is a named setup. You make it by running operations, never by writing rows.

blueprint/starting-worlds/funded.tsexport default Blueprint.startingWorld("funded", {
  from: founded,
  cast: { ada: owner, olga: grantee },
  makes: (s) => [s.ada.run(grant, { organization: s.world.organization, member: s.olga.person, limit: 500n })],
  gives: (s) => ({ organization: s.world.organization, allowance: s.last.allowance }),
});

The empty-handler rule. Before any behaviour exists, the journey author runs the checks against the scaffolds. Every step that needs behaviour must go red. A step that passes on an empty handler is labelled "proved by the description", because the role or state already guarantees it.

$ ortho prove --empty --only "revoke then spend"
  ✘ ada revokes it                 AllowanceRevoked not emitted
  ✘ olga can't spend               not refused: the empty spend ran
  ✔ olga can't revoke it either    proved by the description (the role refuses her)
Today. Executable journeys and starting worlds run on main. There's no prose stage yet, and the model leaves journeys out. Journeys call the server over raw HTTP, so the clients aren't proved. Planned: stories in the model (M1), --empty as a standing check, and journeys through every client (M2).

Blanks and handlers

Handlers built · blanks in the model M1

A blank is anything the description leaves open: a handler body, a journey that is still a story, a question only a person can answer (Blueprint.todo("what happens at the month's end")). The compiler counts blanks, and the factory turns each into a task.

For every operation, Orthograph generates a handler frame: a type that says what the handler is given and what it may return. It also writes a scaffold once into src/, which is yours from then on.

src/allowance/spend.ts// Scaffolded from blueprint/things/allowance/verbs/spend.ts. Yours from now on.
import { Effect } from "effect";
import type { Handler } from "../../generated/api/src/allowance/spend.handler.ts";
import { AllowanceExceeded } from "../../blueprint/things/allowance/errors.ts";

const spend: Handler = ({ allowance, amount }, { steps, instance }) =>
  Effect.gen(function* () {
    const left = instance.limit - instance.spent;
    if (amount > left) return yield* new AllowanceExceeded({ remaining: left });
    yield* steps.record({ spent: instance.spent + amount });
    return { remaining: left - amount };
  });

export default spend;

Generated files open with // Generated from … Do not edit. and are rewritten on every compile. Scaffolds open with // Scaffolded from … Yours from now on. and are never touched again. Errors are values, dependencies are given, and nothing reads the environment.

Data

Database and actor built · stores M1 · sources and views M5 · chain M6

One rule sorts every place data can be. If Orthograph owns the schema and every write goes through Orthograph's commit, the place is a store. If anything else owns it, it is a source, and you reach it through an adapter.

A thing lives in a store. Say nothing and it lives in the project's default store. To keep a group of things apart, declare a store and point the things at it.

blueprint/stores/ledger.tsexport default Blueprint.store.database();
blueprint/things/entry/thing.tsimport ledger from "../../stores/ledger.ts";
export default Blueprint.thing({ description: "…", fields: { … }, lives: ledger });

The kinds of store are open. A host or a language supplies a kind by implementing one port: take a call's writes, events, outbox entries and request key together or not at all, guarded by a version. Orthograph ships three kinds.

KindWhat it isChoose it when
database (default)D1, with a version columnyou need to list and search across many
actorone Durable Object per instance: its own SQLite, one writer at a time, an outboxyou need strict consistency per instance and no lists
chaina contract, generated in the Solidity languageit is money or a public commitment

Others arrive as packages: Postgres or MySQL that you own, SQLite on a device. KV, R2 and caches are never homes, because they can't commit atomically. Files are fields kept in R2, and search indexes are views.

Every store gets the host's default binding, its own D1 named from its path. An environment names a store only to bind it differently. A call commits to one store; work across stores runs as a workflow. Migrations are generated per store. A plugin brings its own stores, named by its mount, so auth's tables never meet yours.

A system you don't own, like a database another team runs, is a source. You mount an adapter for it, and a handler calls it through a step. The call gets its own span and typed errors. The adapter's stand-in is the real database software, loaded from the source's schema, and Orthograph never migrates it.

blueprint/things/shortlist/verbs/add.tssteps: {
  candidate: Blueprint.step.call(bench.calls.candidates.find), // a source, through its adapter
  save: Blueprint.step.database(),                              // our own store
},

Lists across stores and sources are views: read models the system keeps up to date from events. You declare a view the same way as a thing, and its read is generated in the SDK, CLI and MCP.

blueprint/views/allowances-by-organization.tsexport default Blueprint.view(Allowance, {
  from: [allowance.events.granted, allowance.events.spent, allowance.events.revoked],
  key: Allowance.fields.organization,
});

The model generates a data map (generated/data/map.md, and a data page in the portal): every store with its kind, binding and migrations, every source with its adapter and stand-in, and what feeds each view.

Today. lives takes "database" | "actor" (packages/orthograph/src/modules/things/types.ts:32), an environment binds one database, and a list over actor things isn't possible. Decided in design/decisions/K3-stores-and-sources.md.

Traces

Spans built · commit span, text and counts M1

You never write span code. The declaration produces it. Every operation opens one span named after it, but only once the caller has passed the role check, so a refused stranger never looks like work. Every declared step opens a child span, <operation>.<step>, and the commit opens one more. Only public fields become attributes: payload.*, answer.*, principal.person. Free text is left out unless you mark it Blueprint.traced(…).

spend                     principal.person=ada  payload.amount=40  answer.remaining=60  attempt=1
├─ spend.load             step.kind=database
├─ spend.record           step.kind=database
└─ spend.commit           commit.writes=1  commit.entries=1  commit.outcome=committed

What to look for:

  • Red means a defect, and only a defect. A declared refusal ends its span OK, tagged refusal with the log that decided it.
  • A missing child shows where it stopped. spend.load without spend.record means it was refused after the read.
  • attempt above 1, after a commit with commit.outcome=conflict, is a version race.
  • request.replayed=true is a retry that changed nothing.
  • Step widths against the operation's budget show which step is slow.

A bad payload is refused before any span, and a wrong role in its own <operation>.refused span; both are still counted: ortho.calls and ortho.call.duration are metrics for every call. An environment's telemetry list says where it all goes: Telemetry.sink.local() (the Collector and the local viewer) or Telemetry.sink.axiom({ group }).

Today. Operation and step spans, the public-only allowlist and refusals ending OK run on main (packages/language-effect/src/modules/handler/). The commit span, untraced text and call counts are decided in design/decisions/O2-trace-gaps.md.

Plugins

Planned · M1

A plugin is built once, proved in its own CI, and mountable by any project. There are five kinds, and the kind is the whole difference between them. Feature, adapter and projection are planned for M1; language and host are added by K27 and built in Goal 4.

KindAddsExamples
featureto what the system is: things, operations, handlers, journeys, exports. Your app is the root feature@orthograph/auth, @orthograph/organizations, @orthograph/agents, @orthograph/work, @orthograph/wallets
adaptersomething outside: calls out, events in, a service principal, secrets, a stand-in, a conformance test. No things of its own@orthograph/stripe, @orthograph/resend, @orthograph/anthropic, @orthograph/eip1193
projectionwhat it becomes: renders outputs, replays journeys, says where it runs and how it shipsserver, sdk, react, cli, mcp, docs, portal, builder, agents
languagewhat code is written in: the generated frame, the scaffold, the refusal codes, the guards. It writes for store kinds and supplies none@orthograph/language-effect, @orthograph/language-solidity
hostwhere code runs: the place, its store kinds, the wire and the deploy@orthograph/host-cloudflare, Host.node, Host.chain

Every plugin has the same layout:

@orthograph/auth/
  blueprint/
    feature.ts         the descriptor: needs, choices, settings, exports
    things/            person/, session/, api-key/   with verbs/, roles.ts, errors.ts
    journeys/          proved in the plugin's own CI
    starting-worlds/   signed-up.ts
    choices.ts         picked once, when an app mounts it
    settings.ts        given per environment
    secrets.ts         what it needs, by export
  src/worker.ts        its runtime on a Worker
  src/node.ts          its runtime on Node
  skills/              shipped into each app's agent kit
  README.md
@orthograph/wallets/blueprint/feature.ts · a descriptor imports only Effect and the Blueprint APIexport default Blueprint.feature({
  needs: [auth, Blueprint.need(eip1193, { when: Choices.signer.browser.injected })],  // only if that signer is picked
  choices: Choices,
  settings: Settings,
  exports: { Signer },
});
Today. Outputs are fixed renderers (generators/src/modules/render/service.ts:13-24), and auth's things are copied in by the starter. Codex's unmerged D4.md on layer/4 designed the same descriptor under the old plugin word. M1 takes that design and its six checks, under the new names.

Mounting

Planned · M1

A mount is one file: blueprint/<kind>/<name>.ts. The file's name is the mount's name. There is no config file.

blueprint/
  features/auth.ts  features/organizations.ts  features/wallets.ts
  adapters/stripe.ts  adapters/anthropic.ts
  projections/server.ts  projections/sdk.ts  projections/cli.ts  projections/mcp.ts  projections/docs.ts
  environments/local.ts  test.ts  staging.ts  production.ts

A mount can only say four things:

VerbWhat it doesWhy it's safe
choosepicks one of the options the plugin offersthe plugin proved each option in its own CI
includenames which of an adapter's calls and events are reachablethe app reaches only what it named
narrowfewer ways in, fewer callers on an operationfewer callers can't break a journey that passed with more
omitdrops an operationcheck fails if anything still calls it
blueprint/features/wallets.tsimport { Blueprint } from "orthograph";
import wallets from "@orthograph/wallets";

export default Blueprint.use(wallets, (w) => [
  w.choose(w.choices.signer.node.keystore, w.choices.signer.browser.injected),
  w.narrow(w.operations.wallet.link, { allowed: [owner.of("organization")] }),
]);

Choices against settings. A choice changes the model, so it never varies by environment. A setting is a value each environment gives, such as which chains a wallet links for: settings: [wallets.settings.chains.is([1, 8453])] in environments/production.ts.

Needs. A plugin names what it requires. ortho add finds an existing mount that already meets the need, offers to widen one, or mounts it for you. An app mounts each plugin once.

$ ortho add feature @orthograph/wallets
pinned  @orthograph/wallets 1.1.0 (published over three days ago)
needs   auth ✔ mounted   eip1193: only if you choose the injected browser signer
wrote   blueprint/features/wallets.ts

There is no override. If you need a feature's operation to behave differently, write your own operation over what the feature exports.

Languages and hosts

Effect built · Solidity M6 · Noir, Python later

Three separate axes:

  • A language is what code is written in. Each language maps values, gives a runtime, sets the blank format, and runs conformance against the others. This word replaces "target".
  • A host is the machine the code runs on.
  • A projection is the thing you hand someone.
LanguagePackageUsed forStatus
Effect TypeScript@orthograph/language-effectthe server, the SDK, the CLI, handlersBuilt
Solidity@orthograph/language-soliditythings that live on chain; the machine fuzzed against the TypeScript oneM6
Noir@orthograph/language-noirproofs made on the client, verified on chainLater
Python@orthograph/language-pythona Python client, built from the modelLater

The hosts are Host.worker, Host.node, Host.browser, Host.chain, Host.native, Host.python, and Host.world (code used only inside worlds). An operation's runs says where its behaviour executes: server (the default), client or chain.

Principals and ways in

anonymous, person built · the rest M2

A principal is who is calling. Every request comes through a door, the door works out the principal, and roles are checked before any of your code runs.

PrincipalHow it gets inExample
anonymousno credential; only anyone admits itsigning up
personVia.session (browser), Via.key (an ak_ key), Via.device (the CLI's sign-in)Ada grants an allowance
agentVia.agent: an agents-feature run, or an outside agent signed in through MCP OAuth, acting for a persona support agent spends from Bob's allowance
service(<mount>)an adapter's door, verified by the outside system's own schemeStripe settles a payment
systemthe system's own workflows, loops and keepera run finishes; the monthly reset

A role asks which person. .via and .notVia decide which ways in may use it. An agent acting for Ada passes Ada's roles unless the operation says otherwise. Operations that move money out are .notVia(Via.agent) by default.

allowed: [organizations.roles.owner.of("organization").via(Via.session, Via.key)]
allowed: [owner.of("organization").notVia(Via.agent)]            // a refund needs a person
allowed: [Blueprint.role(Payment, { service: stripe })]           // only Stripe may settle
allowed: [Blueprint.system]                                       // only the system's own loop

Each environment says which ways in it issues: issues: [Via.session, Via.key, Via.device, Via.agent].

Today. Principal is anonymous | person (packages/blueprint/src/modules/roles/types.ts:6-8).

Secrets

Planned · M2

A secret is a value the description names but never holds. The plugin that needs it declares it. Its name comes from the mount and the export. Only that plugin's layer ever reads the value, and only as a Redacted.

@orthograph/stripe/blueprint/secrets.tsexport const apiKey = Blueprint.secret.stored({ describe: "Stripe's secret API key, sk_…", test: "sk_test_…" });
export const webhookSigning = Blueprint.secret.stored({ describe: "The endpoint's signing secret, whsec_…" });
@orthograph/stripe/src/worker.ts · the adapter's layer is handed its secret at the composition rootexport const layer = Blueprint.layer(stripe, ({ secrets }) =>
  Effect.gen(function* () {
    const key = yield* secrets.apiKey;          // Redacted<string>: printing it shows <redacted>
    return makeClient({ apiKey: Redacted.value(key) });
  }));
KindUsed byHeld in
runtime (default)a running Worker, actor or workflowthe environment's secret store; secrets.env (0600) locally
releasepromote and publishCI's secrets, never a Worker
builderthe tools that build: the agent harness, benchesthe developer's machine or CI

STRIPE_API_KEY          stored     runtime   set 12 Nov
STRIPE_WEBHOOK_SIGNING  stored     runtime   missing
AUTH_SECRET             generated  runtime   set 2 Nov

Long work: actors, workflows, agent runs

Actors built · workflows M3 · runs M4

Three shapes of durable work, each on its own Durable Objects:

ShapeRuns onUse it for
actora thing with lives: "actor": an Effect Cluster entity, one Durable Object per instanceone writer at a time, its own storage, an outbox
workflowEffect Workflow on Cloudflare: one execution per Durable Object, each step rememberedprocesses that wait: a webhook, a day, a verdict; work across actors
agent runPi Durable inside each run's own Durable Objecta model loop with a transcript, steering, compaction and crash recovery
blueprint/workflows/checkout.tsexport default Blueprint.workflow({
  steps: {
    charge:  Blueprint.step.call(stripe.calls.checkout.sessions.create),
    settled: Blueprint.step.await(stripe.events.checkoutCompleted),   // waits days if it has to
    notify:  Blueprint.step.call(payment.operations.settle),
  },
});

A workflow replays from its top after an eviction, so every step is an activity whose result is stored. Nothing is charged or sent twice.

Chapter 3

Guides

Auth and organizations, end to end

Identity built in the host · plugins M2

Auth is two plugins, because it does two separate jobs:

@orthograph/auth: who is calling

People, passwords and passkeys, sessions, API keys, the CLI's device sign-in, OAuth so a remote agent can use MCP. It declares AUTH_SECRET. Better Auth on D1 runs underneath.

@orthograph/organizations: what you belong to

Organisations, memberships, invitations, the owner and member roles, holds, and the starting worlds founded and invited. It needs auth.

Mount and configure

blueprint/things/agent/verbs/tell.tsexport default Blueprint.operation(Agent, {
  allowed: [Blueprint.system],
  on: [Blueprint.on(Events.SpendAsked, (e) => ({ agent: e.agent, input: e.text }))],   // through the outbox
});

An agent is its own thing, living in its own actor, which holds its Pi Durable conversation. The conversation lasts as long as the agent does, and Pi compacts it. Any operation allowed to create an agent makes one, under its own roles. Events reach the agent through the outbox, by agent.tell: the event's id is Pi's request id, so each input is taken once, a busy agent is steered and an idle one starts a turn. Its tools call as the agent itself, so a role decides what it may do. A run is one input and its answer inside the conversation, not a row. A builder agent is the same feature, given project tools instead of operations (K40).

The factory

Work app declared · factory M3 · agents join M4

@orthograph/work is a feature that builds other projects. It needs auth and organizations. Its own things are missions, milestones, questions, runs and attention. It reaches the project it builds, and the logbook, through adapters.

Tasks are worked out, never stored. They come from the project's model and the facts, and only a fact closes one.

TaskComes fromClosed only by
write:journeya journey that is still a storya check writer's change merged, and the journey failing on empty handlers
build:operationan operation with a blank, or journeys not yet greena green CI verdict at a revision
fix:operationa red verdicta green one
improve:operationa watch finding: over budget, refusals upwatch green over its window
attentiona promote, a secret, money, a questiona person's act

A milestone is a named set of operations and journeys that must be green. It's done when every task under it is closed by a fact.

Chapter 4

Proof and shipping

Proof

Built · through clients M2 · per-operation verdicts M1

A world is a running copy of an environment, made for a purpose and destroyed after, with its own storage, clock and cast. prove makes one, builds each starting world by running operations, plays every journey, and judges the evidence.

  1. A call arrives at a door. The role is checked before any of your code runs.
  2. The state is checked. A move from the wrong state is refused with the generated error.
  3. The handler runs inside spans named by the model: allowance.spend, .load, .record.
  4. The move and the event are recorded, and the answer goes back.
  5. Everything the call left (the caller, the answer or refusal, events, spans, logs) is evidence, filed under model names.
  6. Nine evals judge the evidence against the declaration: answer shape, declared errors, machine path, events, who may call, steps, budget, coverage, explainability.
  7. All of an operation's evals at one revision in one environment make its verdict. Only CI writes verdicts, signed, into the logbook.

The same journey played through the SDK, the CLI and MCP must leave the same evidence. That is how each client is proved, not just the server. A verdict names the model's hash and each handler's hash, so changing a handler makes its own verdict stale and nothing else's.

Ratchets. Once an operation is green, a change that turns it red is refused. Budgets can only tighten.

Stand-ins: local, never fake

Verdaccio in use · the ladder M5 · Anvil M6

Worlds run on real software. When an adapter's outside system can't run locally, the adapter declares what stands in, from the highest rung it can reach. The evidence records which rung was used.

RungWhat it isExamples
1 · real processthe real software, run locallyAnvil for a chain; another Orthograph app's world
2 · compatible real softwarea real program that speaks the same protocolMailpit over SMTP; a local OpenAI-compatible model server; Verdaccio for npm
3 · the vendor's own mockthe vendor's code, labelledstripe-mock
4 · the vendor's sandboxstaging only, with a test keyStripe test mode

Never our own fakes. A conformance test runs the adapter's calls against its stand-in, and in the cloud against the real service, so the stand-in stays honest.

  • Versions are worked out from the model's diff: a new operation is minor, a changed payload is major, a budget is a patch.
  • Watch runs the same evals on what production records. A finding becomes an improve task, and anything about money or security goes to a person.
  • Rollback is promote of an earlier revision. A migration that can't run backwards blocks it, and promote names the migration.
  • Destroy: a world expires on its own alarm, and ortho env destroy <name> removes a cloud environment. Nothing is left running.
