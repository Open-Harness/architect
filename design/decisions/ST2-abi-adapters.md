# ST2-abi-adapters: an adapter made from a contract's ABI

**Decided 22 November 2026 by Goal 12's lead**, under AGENTS.md, "Who decides", in the decision step before ST2.02
(`design/milestones.md`). It builds on K3 (a contract we don't write is a source, reached through an adapter), K7 Q2
(the adapter is generated from their ABI and keyed by their address) and `design/frame/adapters.md` (the six things an
adapter brings).

## The problem

ST2.02 asks for `ortho new adapter --from-abi`, typed calls and events, a stand-in contract deployed into the world,
and an `erc20` adapter over a test token as the first one. Four things were open:

1. **Where the EVM code lives.** Encoding a call, decoding an answer and decoding a revert are viem, and lint keeps
   viem inside `chain-evm`, which is Goal 4's:

   ```ts
   // packages/lint/src/modules/rules/internal/viem.ts:8-13
   meta: { schema: [], docs: { description: "The EVM chain package owns all hand-written viem imports." } },
   if (name === "viem" || name.startsWith("viem/")) {
     context.report({ node, message: "Import EVM functionality from @orthograph/chain-evm instead of viem" });
   ```

   `chain-evm/device` has the port, `decodeRevert` and `makeEventSource`, but no encoder and no read that returns data.
2. **How the types are made.** K7's spike typed calls with viem's inference over an `as const` ABI (`evm#8`).
3. **What a write call does.** Who signs, and what it answers.
4. **Where `erc20` lives,** and what "conformance against the stand-in" means for a contract.

## The call

1. **The codec stays in `chain-evm`**, asked of Goal 4 by #471: `Abi.encodeCall`, `Abi.decodeResult`,
   `Abi.encodeDeploy`, `Abi.refusal` (an ABI error as a `RefusalLockEntry`) and `ChainPort.read` (an `eth_call` that
   returns its data). Untyped at that level. Not chosen: letting a second package import viem (two owners of the EVM
   library, against M1.30's lint), or `ox`/`abitype` directly (the same thing by another name).
2. **The generator writes explicit TypeScript types**, one interface per function's arguments and answer, per event's
   arguments and per error's fields, from the ABI's JSON. No viem type machinery leaves `chain-evm`, and a reader sees
   `{ readonly to: Address; readonly value: bigint }` in the file instead of a type computed from a tuple. The ABI's
   types map as: `uint<N>`/`int<N>` → `bigint`, `address` → `Address`, `bool` → `boolean`, `string` → `string`,
   `bytes`/`bytes<N>` → `Hex`, `T[]`/`T[N]` → `ReadonlyArray<T>`, a tuple → an interface of its named components.
   An ABI the generator can't map (an unnamed tuple component, a duplicate name it can't disambiguate) is refused
   with the item named, never guessed. Overloads are named `<name>_<n>` by their order in the ABI.
3. **Every function is a call, of two kinds** (K7 F1: every function is reachable). A `view` or `pure` function is a
   read: `port.read`, then its answer decoded. Any other function is a write: `prepare`, `simulate` (mandatory, M1.32),
   `sign`, `submit`, answering the `Submission`; a revert in simulation is decoded by the contract's own errors and
   nothing is sent. Both are `effect`-mode callables (`language-effect`'s `calls`), declaring the ABI's errors as
   `Blueprint.error` classes. They need one service, the contract's chain: its `ChainPort`, its address and, for a
   write, a `Signer`. The host or the wallet provides it (the wallet's device half in ST2.03); the adapter never makes
   a key. A revert whose selector isn't the contract's stays `ChainFault`, a defect at the call, as M1.30 says.
4. **Events are typed sources**, one per ABI event: `makeEventSource` over the event item at the contract's address,
   with the generated argument type. They go to the follower (M6.09) and in through `on:` (M5.03); this slice only
   makes them typed and decodable.
5. **Two packages.** `@orthograph/adapters-abi` holds the generator (ABI JSON → planned files; pure, no chain) and the
   runtime the generated files import (read, write, events, errors, the stand-in's deployment, conformance).
   `@orthograph/erc20` is the first adapter, generated by it: its root export is its descriptor, as every plugin's is
   (M1-plugins). Goal 12's brief owns both paths.
6. **`ortho new adapter <name> --from-abi <file>`** is a module in the CLI, which is Goal 3's: it calls the generator's
   `plan` and writes the files, as `add` does. Asked of Goal 3 by an Ask issue; until it lands, the generator's own test
   regenerates `@orthograph/erc20` and fails if the checked-in files differ.
7. **The stand-in is the contract itself, deployed into the world's Anvil** (`Stand.process`). An ABI adapter ships the
   stand-in's bytecode with its source: for `erc20`, an OpenZeppelin ERC-20 with a test mint, compiled and checked in
   with the compiler's version named. Its ABI is the standard's with OpenZeppelin's ERC-6093 errors.
8. **Conformance, for a contract, is the ABI against the deployed code.** It runs every call the adapter declares
   against the stand-in: each read answers and decodes, each write simulates (a write that must revert for want of a
   balance decodes to the declared error), and each declared event is emitted by some write and decodes. A call whose
   selector the code doesn't have (an empty answer, or a revert with no data) is a disagreement, named. The cloud pass
   runs the same against the real contract at its address; that is later (no network now).

## The modules (each its `types.ts`)

`@orthograph/adapters-abi`:

| Module | What it does |
|---|---|
| `generate` | `AbiAdapters.plan({ name, abi, bytecode? })`: the files of an adapter package, each with its header (`// Generated from <abi file>. Do not edit.` or `// Scaffolded from <abi file>. Yours from now on.`); `AbiRefused` names what it can't map |
| `contract` | the contract's chain as a service; `read` and `write` given a function item; the errors' decoding |
| `events` | a typed event source from an event item and the contract's address |
| `stand-in` | deploy the stand-in's bytecode into a world's chain and answer its address |
| `conformance` | run an adapter's declared calls and events against a deployed contract; a report, a disagreement named |

`@orthograph/erc20`: `adapter.ts` (the descriptor, scaffolded), `abi.json` (the contract), `generated/` (the types,
the callables, the events, the errors), `stand-in/` (the token's source and bytecode).

## Not done here

- Wiring a stand-in's deployment into `Worlds.start` (prove, Goal 3's), so a journey's world has the token: asked when
  ST2.04 needs it.
- A write through the browser's wallet (EIP-1193): ST2.03.
- `refusals.lock` codes for an adapter's errors (M6.10, Goal 4): the adapter names its codes `<adapter>.<Error>` until
  then.
