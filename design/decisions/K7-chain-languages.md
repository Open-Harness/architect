# K7: chain languages, worked out together

Written 18 November 2026 by the building agent. It replaces K5's fork Q4 ("how an operation maps to a contract's ABI")
with a war game across three chain languages at once:
- Solidity on an EVM;
- Rust on Solana, with Anchor and without;
- Noir on Aztec.

Aaron then widened the brief the same day, so it also designs the wallet plugin, the first plugin we build. Where this
record and K5 disagree about anything on chain, this record wins. The evidence is one spike in three parts,
`spikes/chain-languages/`, which ran the same mini DAO on all three local chains.

## Aaron's words

- "we should be doing the solidity and the noir at the same time … And then if it's not too much, I would also like
  to do the Solana version … so we can figure out like, okay, where are the edge cases? What are the exceptions and how
  do we handle them?"
- On K5's Q4: he leans to A (the operation is the function) for our own contracts. "Other people's contracts are
  sources, reached through adapters" (K3 item 8). We can be opinionated about how we write our own contracts, but we
  can't rely on that for other people's.
- On Q4's option C: he asked what "unsafe" meant. It never meant the contract was unsafe, because a contract enforces
  itself whatever calls it. It meant that the generated SDK and agent tools would advertise helper functions the
  blueprint never declared, with no roles or journeys behind them.
- Agent-native is dropped as a runtime; only its shapes are kept. Agents will be durable, on a different stack.
- On the wallet plugin: "I think I need to be able to create a plugin. And that's what we're going to be doing at the
  very first … that plugin is going to be a something that goes on chain. So a wallet plugin, basically… what should
  be in the scope of that? Should we just do an EVM one? We've got three chains… Should it have server side, client
  side?"

## The answer in one breath

**Our own programs are stores, and each declared operation is exactly one generated entry on the chain. A generated
manifest says which entries those are, and `ortho check` refuses any other entry that can change state. Other people's
programs are sources: an adapter typed from their interface, never a store. On every chain the SDK simulates first,
decodes every refusal to the same typed class with the same code, and calls a submission `confirmed` only when the
follower has seen the declared event for that intent at the environment's confirmation level.**

The three chains need the same eight answers, and they give them in different words. Most of the edge cases are in
those differences, and each one has a rule below.

## The worked example, and what ran

The example is the community workshop's mini DAO from K5. A member votes once per proposal, and the tally is public.
Publishing links a D1 revision to a confirmed `ProposalOpened` event. On Aztec, membership is private, a one-use claim
per proposal stops a second vote (Aztec calls it a nullifier: a public mark that the claim was used, which nobody can link to the
member), and the tally is still public. The blueprint, with its refusal codes, is
`spikes/chain-languages/spec.md`:

// generated by the runtime: NotAllowed (role check failed: not admin / not a member)        // AR-001

Each folder's README has the numbered findings with their evidence files. This record cites them as `evm#n`,
`solana#n` and `aztec#n`.

## The rule that sorts every case

K3's rule, carried onto chain: **if Orthograph generated the program and every write goes through its generated
entries, it is a store. If anyone else wrote it, it is a source, reached through an adapter.**

This settles two of the ledger's open rows. `STO-02` and `X-18` asked whether a chain passes K3's commit test. A
transaction is atomic, and the program is the only writer of its own state, so it does. What differs is time: the
commit's answer arrives later, as a submission (Q3 and Q6), not as `committed` or `conflict` on the spot. **K3 gains one
sentence: a store kind may answer a commit late, and then its caller gets a submission.**

## Q1. What runs on chain for one operation, and what clients may call

**In plain words.** A blueprint declares `proposal.vote`. Something on the chain has to run it. Each chain calls that
thing by a different name:
- on an EVM it is a function in the contract's ABI;
- on Solana it is an instruction, together with the list of accounts it touches;
- on Aztec it is a private function, or a public one, or a pair of them.

The developer will also write helpers: small functions that read a tally, or that do arithmetic. The question is which
of the chain's callable entries the generated SDK, CLI and agent tools should offer, and what happens to everything
else.

**On each chain** (all three are hand-written in the shape a generator would emit):

```solidity
// spikes/chain-languages/evm/src/Governance.sol:62-64: generated. Role, machine, then the developer's body
function vote(bytes32 proposal, Choice choice) external {
    _cast(msg.sender, proposal, choice);
}
// spikes/chain-languages/evm/src/MiniDao.sol:52-54: the developer adds an external function no operation declares
function forceClose(bytes32 proposal) external {
    _proposals[proposal].state = State.Failed;
}
```

```rust
// spikes/chain-languages/solana/programs/governance/src/lib.rs:62-67: one instruction per operation
pub fn vote(mut ctx: Context<Vote>, id: u64, choice: Choice) -> Result<()> {
    let a = &mut ctx.accounts;
    let (pid, vr_bump) = (ctx.program_id, ctx.bumps.vote_record);
    do_vote(pid, &a.workshop, a.voter.key(), &a.member, a.gate_token.as_ref().map(|g| g.as_ref()), &a.proposal,
        &mut a.vote_record, vr_bump, id, choice)
}
```

```rust
// shape of spikes/chain-languages/aztec/contracts/governance_contract/src/main.nr:76-84, 95-97: one operation, two functions
#[external("private")]
fn vote(proposal: Field, choice: bool) {
    let voter = self.msg_sender();
    let mine = self.storage.members.at(voter).get_notes(NoteGetterOptions::new().set_limit(1));
    assert(mine.len() == 1, "[AR-001] NotAllowed");
    self.storage.vote_claims.at(proposal).at(voter).claim();   // the one-use claim
    self.enqueue_self._tally(proposal, choice);                // the public half, run later in the block
}
#[external("public")]
#[only_self]
fn _tally(proposal: Field, choice: bool) { /* machine check, tally, VoteCast */ }
```

What each chain's own interface file says, compared with what the generated clients need:

| | EVM ABI | Solana IDL (Anchor) | Aztec artifact |
|---|---|---|---|
| Entry identity | 4-byte selector of `name(types)`; names can be overloaded (`evm#1`) | 8-byte discriminator of `global:<name>` (`solana#2`) | selector, plus a visibility class: private, public or utility (`aztec#2`) |
| Roles, machine, refusal codes | none (`evm#3`) | none; it doesn't say which signer is "the admin" (`solana#3`) | none; role checks live in the body (`aztec#3`) |
| Which errors an entry raises | errors are contract-wide, library errors included | errors listed, by number | assert strings in an error table, but not formatted ones (`aztec#2`) |
| What it carries that the others don't | events with `indexed` | every account, with signer and writable flags and PDA seeds (a PDA is an account address derived from fixed words, so the client can work it out) | private or public, `only_self`, `view` |
| What hides a state change | nothing; the ABI is complete | `remaining_accounts` and CPIs (one program calling another); a read-only instruction can still emit events (`solana#3`) | a public function without `view` looks the same as an operation (`aztec#2`) |
| The trap for a classifier | match by full signature, never by name (`evm#1`) | the IDL lists everything in `#[program]`; a plain `pub fn` is invisible (`solana#1`) | public functions sit in `nonDispatchPublicFunctions`; reading only `functions` misses three of four (`aztec#1`) |

**What the spike found that decides it.** A behavioural cross-check never finds an undeclared entry such as
`forceClose`, because the sequences only call declared operations (`evm#5`). Only a static check over the compiled
interface catches it, and all three classifiers did: EVM exit code 3 on `forceClose` (`evm#1`), Solana three
undeclared instructions (`solana#1`), Aztec `rewrite_digest` (`aztec#1`). None of the three interfaces says which
entry belongs to which operation, so that has to come from us.

**Decided, then changed by Aaron's F1 answer (18 November 2026).** He wants every function reachable, for programmatic
access, with roles generated into our opinionated scaffold. So the manifest now lists every external function, and the
clients are generated from it, helpers included. A hand-written external function that changes state must use a
generated role modifier, and `ortho check` warns when it has none, rather than refusing it. Items 1 and 4 stand as
written. Items 2 and 3 below are the original version, kept for the record:

1. **Each operation is one generated entry**, or on Aztec one generated pair: a private entry plus an `only_self` public
   continuation. The developer writes only the body.
2. **The generator writes a surface manifest** beside the program, `generated/<language>/surface.json`. For each
   operation and declared read it records the entry's signature and selector (or discriminator), the role, the
   refusals and the events. On Solana it also records the account list with its seeds, and on Aztec the visibility and
   the continuation. The SDK, CLI, MCP tools and actions are generated from the manifest, never from the chain's
   interface.
3. **`ortho check` classifies the compiled interface against the manifest**, by full signature, and refuses an entry
   that can change state when no operation declares it. A helper the developer means to keep public is marked
   `Blueprint.outside("why")` in the body file's NatSpec, or in its Rust or Noir attribute. It then passes the check,
   and no generated client reaches it. Read-only helpers (`view`, `utility`, an instruction with no writable accounts)
   pass without a mark, but they never become SDK methods. On Solana and Aztec, "read-only" is taken from the
   manifest, not from the interface: there, an entry the interface calls harmless can still emit events or change
   state.
4. **Generated helper entries** (`admin()`, `nonces()`, `eip712Domain()` on an EVM, and Solana's
   `initialize_workshop`) are listed in the manifest as `generated`, so the check never asks about them (`evm#2`,
   `solana#1`).

## Q2. Contracts we don't write

**In plain words.** Other people's programs are already on chain: tokens, other protocols, Solana's token program.
They will never follow our conventions. K3 says such a thing is a source, reached through an adapter whose typed calls
and events are generated from its interface, and never a store we own. The spike tested that on all three chains, in
two ways:
- reading their contract from our TypeScript;
- having our contract call theirs, by gating the vote on holding one unit of their token.

**On each chain:**

| | EVM: an OpenZeppelin ERC-20 | Solana: SPL Token | Aztec: the stock `Token` |
|---|---|---|---|
| Typed adapter from their interface | yes: viem with an `as const` ABI; `tsc` refuses wrong names and types (`evm#8`) | yes, from their account layouts; SPL Token has no IDL of the Anchor kind (`solana#5`) | yes, from their artifact (`aztec#4`) |
| Their events | `Transfer` logs | **none**: follow the accounts, or parse instructions (`solana#5`) | public events only; private transfers show nothing (`aztec#4`) |
| What an outsider can't see | nothing | nothing | private balances: 40 privately minted units read as 0 (`aztec#4`) |
| Our contract calling theirs | works; it adds a refusal the blueprint didn't have, `NoToken` (`evm#9`) | works; the client must pass one more optional account, and our program must check that account's owner (`solana#6`) | not a read at all. It needs a private spend backed by an authorisation witness (`aztec#6`, not tested) |
| How their failure reaches us | their selector, typed only with their ABI; out of gas inside their code looks like an empty revert; "not a contract" can't be caught (`evm#10`) | `Custom: 1`, the same shape as our own error 1; only the logs say which program failed (`solana#7`) | no code of ours (`aztec#5`) |

**Decided.** K3's idea holds on all three chains, and Aaron's rule stands: a contract we don't write is a source.
- **Reading theirs.** The adapter is generated from their ABI, IDL or artifact, and is keyed by their address or
  program id. It offers typed reads and events in through `on:`. On Aztec it offers public reads and public events
  only, and anything private is marked device-local. On Solana, where SPL Token has no events, the adapter follows
  accounts.
- **Calling theirs from ours.** A call from our program into theirs is a declared step of the operation, with its own
  declared refusal. The generator wraps the call so that whatever they fail with arrives as that one refusal, carrying
  their address and their raw error:
  - EVM: `try`/`catch`, after an explicit check that the address has code;
  - Solana: the failing program's id, read from the logs;
  - Aztec: there is no wrapper, so their refusal is the operation's "outside refused".

  The client decodes their raw error with their interface when it has one, and otherwise it stays `unknown`.
- **What the blueprint must say.** It names the outside program the operation reads: `gate: Blueprint.step.read(spl.
  accounts.token)`. On Solana that is what makes the generator emit the owner check (`solana#6`) and the optional
  account in the manifest.
- **Never a store.** No migrations, no version and no follower checkpoint of ours over their state, other than reading
  their events.

## Q3. Who signs, who pays, and what `confirmed` means

**In plain words.** Someone proves they agree to the vote: a signature, or on Aztec a proof. Someone sends it to the
chain and pays the fee. Those can be two different parties: the member signs, and a relayer pays. Then the app needs
to know when the vote has really happened. K5 gave the SDK `sent.confirmed` for that. What does "confirmed" mean on
each chain?

**On each chain:**

| | EVM | Solana | Aztec |
|---|---|---|---|
| Who agrees | the member's key: a direct transaction, or an EIP-712 signature that any relayer submits (`evm#11`) | the member, as a second signer on a transaction whose fee payer is the relayer (`solana#8`) | the member's own PXE (the private execution environment: the wallet-side process that holds keys and notes and proves) makes the proof, in about 5.6 s; a relayer with no key can submit the proven bytes (`aztec#7`) |
| Who pays | the sender: the member, or the relayer | the fee payer, and whoever is named `payer` pays rent; these are separate roles (`solana#8`) | the sponsor, through sponsored fees; it pays even for a transaction that reverts (`aztec#9`) |
| How long a signature stays good | until its deadline and nonce | **about 60 s at mainnet speed**: the signature covers a recent blockhash, so a late signature can't be refreshed; a durable nonce makes it wait (`solana#9`) | until the proof's anchor block expires (the prior spike: 23 hours) |
| Racing submitters | a second relayer's transaction mines as a revert while the vote is on chain (`evm#14`) | the same signature can't land twice | the second submission is "Existing nullifier" |
| What the public sees | the voter (a relayed vote needs `voter` in `VoteCast`, since `msg.sender` is the relayer) | the voter | the sponsor as fee payer; the **choice** is public calldata; the voter is not (`aztec#8`) |
| Confirmation levels seen locally | Anvil derives `safe` as 32 blocks back and `finalized` as 64; these are depth in disguise (`evm#22`) | processed 0.17–0.64 s, confirmed 0.19–0.70 s, finalized 15.3–19.1 s (`solana#10`) | pending 68 ms, proposed 2.29 s, proven 2.57 s; finalized never arrived within 240 s (`aztec#10`) |

**The edge case that decides it.** On an EVM, two relayers raced one signature. Both simulated cleanly. The first
landed, and the second mined as a revert, yet the vote was on chain (`evm#14`). "My transaction succeeded" and "the
vote happened" are different facts.

**Decided** (the level is fork F2 in the round):

- **A submission has one lifecycle on every chain:** `simulated → submitted → included → confirmed`, ending in either
  `dropped` or `reverted`, and with `corrected` possible after `confirmed`.
- **`confirmed` means the follower saw the declared event for this intent at the environment's confirmation level.**
  For a vote the intent is `(proposal, voter)`. It never means "my transaction succeeded", so a lost race still
  confirms, because the vote happened.
- **`dropped`** means the intent can no longer land:
  - EVM: the nonce was used by something else, or the deadline passed;
  - Solana: `lastValidBlockHeight` passed;
  - Aztec: the transaction was dropped.
- **`reverted`** means it was included but refused. It carries a code only when one could be recovered: by trace on an
  EVM, from the transaction's return data on Solana. On Aztec it carries none, and the client simulates again
  (`aztec#13`, `#16`).
- **The level is a setting per environment and per chain**, and an activity that has an outward effect (the publish
  link, a forum post) waits for `final`.
- **Signing on Solana is just-in-time.** The client signs at send, or uses a durable nonce when a person signs ahead,
  because a pre-signed transaction dies in about a minute (`solana#9`).

## Q4. Where state lives, and what `lives: Blueprint.chain(...)` means (superseded by K25, 20 November 2026)

**In plain words.** A thing that lives on chain keeps its facts somewhere: in contract storage, in accounts, or in
private notes. The client may have to know where they are before it can even make the call. K3 named one store kind,
`chain`. Does one kind cover all three, or do they split?

**On each chain:**

| | EVM | Solana | Aztec |
|---|---|---|---|
| Where the proposal lives | contract storage, slot 4 (`evm#6`) | its own account, a PDA at `["proposal", workshop, id]`, 90 bytes, rent 1,517,280 lamports (`solana#12`) | public storage, read by anyone through the node (`aztec#11`) |
| Where "who voted" lives | a mapping in storage | one VoteRecord account per voter, rent 1,412,880 lamports and never reclaimed (`solana#12`) | a nullifier: public, but unlinkable without the member's key (`aztec#11`) |
| Where membership lives | a mapping | one Member account per member | a private note held by the member; **the admin knows the list** because it made the notes (`aztec#11`) |
| What the client must know | the address and the ABI; the EIP-712 domain for the relayed path | **every account**: 8 slots for `vote`, derived from seeds, with no chain read; whether a gate account is needed it can't tell (`solana#11`) | the contract registered in its own PXE, and its own keys; a second device with the same keys sees membership in 628 ms (`aztec#12`) |
| A limit the blueprint must respect | gas | 1,232 bytes per transaction (the measured vote is 452), and an account limit per transaction not measured here; rent; every vote write-locks the same Proposal account (not measured) | proving time; note growth |

**Decided.**
- **`chain` is a family, and each chain is a store kind**, supplied by its language package (K3 item 2's open list) (superseded by K27, 20 November 2026: supplied by its host, `Host.chain` for `evm`, and written for by its language):
  - `evm`, from `@orthograph/language-solidity`;
  - `solana`, from `@orthograph/language-solana` (Anchor 1.2.2);
  - `aztec`, from `@orthograph/language-noir`.
- **Each kind declares its capabilities.** The compiler refuses what a kind can't serve, as it already refuses a list
  over actors:
  - every kind: `pending`, meaning the commit answers late;
  - `solana`: `accounts`, meaning every operation has an account list and rent;
  - `aztec`: `private`, meaning notes, nullifiers and device-local reads. This defines ledger row `G-04`.
- **`lives` names the kind:** `lives: Blueprint.chain.evm({ contract: "Governance", per: "workshop" })`, and likewise
  `.solana(...)` and `.aztec(...)`. `Blueprint.chain({...})` alone means `evm`, so K5's sketch still reads right. (Superseded by K25, 20 November 2026: a chain store file, `Blueprint.store.chain.evm()`.)
- **On Solana the account list is part of the client contract.** The manifest holds each operation's accounts and
  their derivation, and the generated client is an account resolver plus an encoder (`solana#11`). An account that is
  needed only sometimes, like the gate token, is declared in the blueprint, because the IDL can't say when.
- **On Aztec the "sync first" step is the SDK's job.** Utility reads sync on demand in 5.3.0 (`aztec#12`), so no
  handler ever sees it.

## Q5. Refusals: one code, three wire formats

**In plain words.** The blueprint declares `AlreadyVoted` with code `PR-001`. Whichever chain refuses, the app must
get back a typed `AlreadyVoted` carrying `PR-001`, and an old client must still decode a newer contract. Each chain
carries an error differently, and each has its own way of losing the code.

**On each chain:**

```solidity
// spikes/chain-languages/evm/src/Governance.sol:16-19: one custom error each; its wire identity is a 4-byte selector
error AlreadyVoted(bytes32 proposal);   // PR-001
error ProposalExists(bytes32 proposal); // PR-002
error ProposalNotOpen(State state);     // PR-900 (Absent = "never opened")
error NotAllowed();                     // AR-001
```

```rust
// shape of spikes/chain-languages/solana/programs/governance/src/errors.rs:6-15 (condensed): numbers pinned by hand, in the 6000 block
#[error_code]
pub enum GovernanceError {
    #[msg("PR-001 AlreadyVoted")] AlreadyVoted = 1,        // 6001
    ProposalExists = 2, ProposalNotOpen = 900, NotAllowed = 1001,   // 6002, 6900, 7001
}
```

```rust
// spikes/chain-languages/aztec/contracts/governance_contract/src/main.nr:80 and :100: the code rides in the assert's text
assert(mine.len() == 1, "[AR-001] NotAllowed");
assert(state == OPEN, f"[PR-900] ProposalNotOpen {{ state: {state} }}");
// and AlreadyVoted has no assert at all: a second vote is a nullifier collision
```

**What makes a code unstable.** This is where the three differ most:

| Change | EVM | Solana | Aztec |
|---|---|---|---|
| Rename the error | the selector moves, and an old client loses the code (`evm#19`) | the number is kept | free, if the client matches on `[PR-001]` (`aztec#17`) |
| Add or retype a field | the selector moves (`evm#19`) | the number is kept; payloads ride in return data (`solana#15`) | a formatted message silently loses `state` (`aztec#17`) |
| Reorder the declarations | the selector is kept, but **a code taken from order silently swaps PR-001 and PR-002** (`evm#19`) | **every number shifts**, unless they're pinned (`solana#13`, `#14`) | not on the chain |
| Refusals that arrive with no code of ours | an empty revert, an out-of-range enum, out of gas with no data, a mined revert with no reason (`evm#17`) | Anchor's own errors (2006, 3010, 3012, 3005), System `Custom: 0` and `1`, compute exhaustion (`solana#18`) | `only_self`, overflow inside Token, not deployed, a mined revert with "Reason: unknown" (`aztec#16`) |
| A refusal that is not ours at all | `InvalidNonce` hides `AlreadyVoted` on a replay (`evm#12`) | `init` of an existing account: the System Program refuses before our code runs (`solana#16`) | `AlreadyVoted` **is** a nullifier collision, with three texts from three layers (`aztec#13`) |

**One rule held on all three:** the order of the checks. The Effect wrapper checks the role, then the machine, then the
body. Two chains break that order by themselves:
- **Anchor** validates accounts before the handler runs. With a plain `init` vote record, the cross-check diverged 271
  times in 1,500 steps (`solana#17`).
- **Aztec** checks membership and the claim on the device, but the machine state only later, in the block. A repeat
  voter on a closed proposal therefore got `PR-001` where the reference said `PR-900` (`aztec#26`).

**Decided.**
1. **Refusal codes go into a lock**, `blueprint/refusals.lock`. It is generated, checked in and append-only, and it
   holds each code, its error, and its wire identity on each language: the EVM selector and signature, the Solana
   number, and the Aztec text. Codes are never taken from declaration order again. Today they are
   (`packages/compiler/src/modules/model/internal/describe.ts:79`, `i + 1`), so reordering two errors would silently
   swap their codes on every language, Effect included. Changing an error's shape gives it a new wire identity, and
   the old one stays in the lock and keeps decoding. A rename of a published code is refused.
2. **Per chain:**
   - EVM: one typed custom error per declared error, decoded by selector from the lock. That keeps typed errors in the
     ABI and in explorers, at 4 to 36 bytes. A single `Refused(code, data)` error was prototyped (`evm#20`) and is kept
     only for clients that must decode contracts older than their lock.
   - Solana: explicit discriminants from the lock, in the 6000 block: `PR-001` → 6001, `PR-900` → 6900, `AR-001` →
     7001. A payload goes in a log line and in return data.
   - Aztec: `[CODE] Name` as the assert text, decoded from `originalMessage`, never from the whole message, which
     embeds source text (`aztec#17`). A refusal with no assert, like `AlreadyVoted` as a nullifier collision, is
     mapped in the manifest per operation: `{ op: "proposal.vote", nullifier: "vote_claims", refusal: "PR-001" }`.
3. **The generated client pre-checks in the reference order on every chain.** That means simulating with `eth_call`
   or `simulateTransaction` (`sigVerify: false`, which costs nothing, `solana#19`), or on Aztec running the utility
   reads (`is_member`, `get`, `has_voted`). This closed every divergence on Aztec (`aztec#26`). The program stays the
   authority, and a pre-check only refuses early. Simulation is not optional, because nothing else does it: Anvil mined
   a transaction that was bound to fail (`evm#18`).
4. **On Solana, any account whose absence is a refusal is generated as an unchecked account and loaded by hand**, with
   its owner and discriminator checked, so that the role, machine, body order survives Anchor (`solana#17`). The vote
   record uses `init_if_needed` plus a flag, so a second vote is our `PR-001` (`solana#16`).
5. **The decoder has one more class: no code.** It covers a panic, a bare revert, a runtime fault, an Anchor framework
   error, a System error, a mined revert with no reason, and an outside program's failure. Each arrives typed as
   `ChainFault { kind, program, raw }`: a defect, not a declared refusal.
6. **Relayed-path refusals** (`InvalidNonce`, `SignatureExpired`, and Solana's `BlockhashNotFound`) are generated
   refusals with `AR-` codes, like `NotAllowed`, so the relayer and the signer see the same typed reason.
7. **K5's sketch declared `NotAMember` beside `allowed: [member]`.** The role check already refuses a non-member with
   `NotAllowed`, so `NotAMember` could never fire. `ortho check` warns when a declared error is never reachable after
   the role check. The workshop drops it.

## Q6. Events, the follower, and when a chain takes something back

**In plain words.** The portal, the publish workflow and any `on:` handler learn about a vote from the chain's events,
read by a follower. A chain can also take back something it showed: a reorg on an EVM, a dropped fork on Solana, a
pruned block on Aztec. The follower has to notice, and has to say so.

**On each chain:**

| | EVM | Solana | Aztec |
|---|---|---|---|
| Where events are | logs, read with `eth_getLogs` and a checkpoint | `emit!` puts them in logs; `emit_cpi!` puts them in inner instructions, which a logs-only follower never sees (`solana#22`) | public logs, through `getPublicEvents`, with no wallet needed (`aztec#18`) |
| How an event can be lost | it can't, short of a reorg | **logs are capped at 10,000 bytes per transaction**: a long log silently dropped the event and even the `success` line from a transaction that succeeded (`solana#23`) | private events reach only their recipients (ledger `AZ-20`) |
| How a take-back shows | **silently**: after `anvil_reorg`, `getLogs` just returns nothing, so the follower has to compare stored block hashes (`evm#24`) | not forceable on a single-node validator (`solana#24`, not tested) | `rollbackTo(n)`: the transaction became `dropped`, its event disappeared, and a contract deployed in that range went missing (`aztec#21`) |
| The publishing link | `digest` matched `keccak256(body)` (`evm#23`) | matched `sha256(body)` at confirmed (`solana#21`) | matched `sha256ToField(body)`, a `Field`, which loses the top bits of a 32-byte digest (`aztec#19`) |

**The edge case that decides it.** With a depth-3 policy, a depth-3 reorg that replayed a different digest for the
same proposal produced `confirmed`, then `correction { wasConfirmed: true }`, then `confirmed` again with
`digest-mismatch`. The publishing link flipped (`evm#24`).

**Decided.**
- One follower per program (M6.09).
- **The checkpoint is a block number plus a window of block hashes.** A take-back is detected by comparing hashes on
  an EVM, by status on Aztec, and by commitment on Solana.
- **A correction is an event of its own**, `<Event>Corrected { wasConfirmed }`. The portal, views and workflows must
  handle it, because a depth policy can confirm something and then retract it. A replacement can even carry a
  different payload.
- **On Solana the follower reads `emit_cpi!` events or account state, never logs alone.** The generator uses
  `emit_cpi!`.
- **The digest the publish workflow links is the chain's own hash**: keccak on an EVM, sha256 on Solana, and on Aztec
  the sha256 reduced to a `Field`, recorded beside the revision. The revision stores which one it used, so the link
  check compares like with like.
- A refused call leaves no event on any chain, so refusals belong to the submitter's receipt, not the follower
  (`evm#23`).

## Q7. Local worlds, and proving a proof locally

**In plain words.** Every journey runs against a real chain on this machine, never a fake one (G1, "local, not
fake"). Each chain ships a local version. They differ in what is real, and the Noir spike's local network skipped
proof verification (`spikes/noir-private-core/README.md:15`), so nothing it proved about proofs was true.

| | Anvil | `solana-test-validator` | Aztec |
|---|---|---|---|
| Start | 156 ms; instant mining 27 ms per transaction (`evm#26`) | 0.5 s; deploy 4–5 s; first build downloads 430 MB of platform-tools (`solana#25`) | the CLI network takes 26 s; in process, 1.0 s with proof checks off and 4.9 s with them on (`aztec#24`) |
| Real | EVM semantics, gas, `ecrecover`, revert data | the SBF VM, compute units, fees, rent, signature checks, write locks, SPL programs | private execution, client proofs (when on), nullifiers, public execution |
| Not real | consensus, fee market; `safe` and `finalized` are depth (`evm#22`, `#28`) | forks, consensus, leader schedule; no rollback can be forced | real epoch proofs and L1 settlement; gossip verification |
| Take-back on demand | `anvil_reorg [depth, txs]`, positional (`evm#24`) | none | `rollbackTo(n)` on the admin API, with one unexplained result (`aztec#21`) |
| Watch out | the banner prints dev keys: always `--silent`; viem's 4 s polling default makes a 35-transaction script take 2.5 minutes (`evm#26`) | Anchor's TS client still needs `@solana/web3.js` 1.x | the CLI network prints test secrets at startup |

**Proof verification, the main new result (`aztec#22` to `#25`):**
- **The CLI network can't verify client proofs.** `aztec start --local-network` hard-codes `realProofs: false`
  (`dest/local-network/local-network.js:104` in 5.3.0), and its node then uses a test verifier that accepts any proof.
  Forcing verification at startup aborts the network, because its own setup transactions carry mock proofs.
- **The in-process network can.** `setupLocalNetwork` from `@aztec/aztec/testing` (the same code path) with
  `realProofs: true` verifies every client proof at admission. Same flow, same harness:

| Submitted | Verification on | Verification off |
|---|---|---|
| an honest proof | accepted | accepted |
| one proof field changed | **rejected**, `Invalid tx: Invalid proof` | accepted, and the vote counted |
| an empty proof | **rejected** | accepted, and counted |
| a random proof | **rejected** | accepted, and counted |

- Verification costs about 50 ms per transaction at admission.
- **What stays unverified locally:** rollup proofs, epoch proofs and their settlement on L1, and gossip verification.

**Decided.**
- Each chain kind supplies its world's stand-in as `Stand.process` (M6.06): Anvil, the Solana validator, and Aztec's
  in-process network.
- **Aztec worlds run in two modes:**
  - **`proofs: "verified"`**, the in-process network with `realProofs: true`. Any claim about proofs (a forged proof
    is refused) runs only here.
  - **`proofs: "mock"`**, which is fast and fine for logic and the long cross-check.

  The verdict says which mode it came from.
- **S30 changes.** A local verifying world now exists for client proofs, so "proofs not verified" applies only to
  mock-proof verdicts. A production promote still needs a verdict from a network that also verifies rollup proofs,
  which no local world gives. This updates ledger rows `PRF-06` and `AZ-10`.
- A Solana world can't test a rollback, so a journey that needs one is marked network-only (the `test: "network"` kind
  from N1).

## Q8. The same machine on every chain (S26)

**In plain words.** The blueprint's machine is generated into every language. The cross-check runs the same random
sequences through the TypeScript machine and through each chain's program, and after each step both must agree on
the state, the tally and the refusal code.

**Found.**
- 0 divergences on all three chains (EVM 1,500 steps, Solana 1,500, Aztec 200 with real proofs plus 900 with mock
  proofs).
- Each harness also failed when it should have:
  - a mutant EVM contract where ties pass gave 457 divergences (`evm#30`);
  - Solana's `init` variant gave 271 (`solana#26`);
  - Aztec without the client's pre-check gave 126 (`aztec#26`).
- The Aztec divergence was a real difference in check order, and the cross-check is what found it.
- A cross-check never finds an undeclared entry, because it only calls declared ones (`evm#5`). That is Q1's static
  check, which is a separate proof.

**Decided.**
- **One reference machine, generated as TypeScript from the blueprint**, and one set of fixed seeds. They run against
  every chain the blueprint targets: in `ortho check` with a few hundred steps, and in CI with the long run (S26).
- **Each chain runs it in its fastest honest mode:**
  - EVM: instant mining;
  - Solana: 100 ms slots;
  - Aztec: mock proofs for the long run, plus a short run with real proofs.
- **The cross-check drives the generated client, pre-check included,** because on Aztec and Solana the client's order
  is part of the behaviour.
- **Every chain's harness carries a planted mutant**, so a harness that can't fail is caught.

## Where the three chains differ, at a glance

Said in two sentences: an EVM is the simplest, because the ABI is complete and state is just storage. Solana makes the
client name every account and checks accounts before our code runs, and Aztec splits each operation between the
device and the block and hides who did what.

| Question | EVM (Solidity) | Solana (Anchor) | Aztec (Noir) |
|---|---|---|---|
| 1 · one operation is | an external function, plus `<op>BySig` when signed | an instruction plus its account list | a private entry plus an `only_self` public continuation, or one public function |
| 1 · the trap | overloads: match by signature | `remaining_accounts` and CPIs hide changes | a public function looks like a view |
| 2 · their contract | ABI adapter; wrap calls to them | layout adapter; check their owner; no events | artifact adapter; public only; a private gate is a spend |
| 3 · who pays | sender or relayer | fee payer, and a separate rent payer | the sponsor, even for a revert |
| 3 · signature lifetime | deadline and nonce | about 60 s; durable nonce | the proof's anchor |
| 3 · what is public | the voter | the voter | the choice, not the voter; the admin knows members |
| 4 · state | storage | accounts with rent | public storage, notes and nullifiers |
| 4 · the client must know | address and ABI | every account | its own notes in its PXE |
| 5 · code on the wire | selector of a custom error | 6000 + number | assert text, or (op, nullifier) |
| 5 · what moves a code | rename, a field change; reorder if taken from order | reorder, unless pinned | a code-text rename |
| 5 · order of checks | role, machine, body | accounts first: unchecked plus a manual load | device first, then the block |
| 6 · events | logs | `emit_cpi!` or account state; logs truncate | public logs only |
| 6 · take-back | a silent reorg: compare hashes | a dropped fork (untestable locally) | a pruned or dropped block |
| 7 · local proofs | not applicable | not applicable | verified only in process with `realProofs` |

| # | Exception | Chain | Handled by |
|---|---|---|---|

## The wallet plugin

Aaron wants the first plugin we build to be one that goes on chain: a wallet. The frame already walks through
writing `wallets` (`design/frame/writing-a-feature.md`):
- eight operations, three of which run on the person's device (`create`, `import`, `keys`);
- `link` as a client operation over two server operations;
- the server never holds a key (dropped by Aaron in F5, see below);
- "wallets needs auth, not chain".

The SIWE linking spike proved linking for real (26 checks, `spikes/authenticated-siwe-link/README.md`). The war game
changes four things in that walkthrough.

1. **Its values are EVM-only.** `Address` is 20 bytes, `ChainId` is an EIP-155 integer, and `Signature` is 65 bytes
   of EIP-191 (`writing-a-feature.md:69-75`). A Solana address is a 32-byte ed25519 key. An Aztec address is an
   account contract's address, and its keys are a signing key plus nullifier and viewing keys inside a PXE (`aztec#12`).
   **Decided:** the `Wallet` thing holds a CAIP-10 account (`eip155:31337:0xab…`, `solana:<genesis>:<base58>`), and
   `chain` is a CAIP-2 id. Each chain family then supplies its own `Address` and `Signature` values. Solana and Aztec
   slot in without reshaping the thing.
2. **"Needs auth, not chain" is true of linking, not of sending.** Signing a SIWE message needs no chain client. But
   Aaron's wallet "goes on chain": it signs, simulates, sends and confirms. That half needs a chain adapter and no
   auth. **Decided:** the wallet has two halves.
   - **The device half** (`runs: "client"`): `create`, `import`, `keys`, the `Signer` export, and a `Submit` export
     that runs Q3's lifecycle (`simulated → submitted → included → confirmed`). It needs a chain adapter. It does not
     need auth.
   - **The linked half** (server, plus `link` on the device): `challenge`, `complete`, `unlink`, `list`. It needs
     `@orthograph/auth` (M2.05).
3. **The chain adapter is a port per family**, so Solana and Aztec arrive as packages, not as a reshape:

   ```ts
   // the port each chain adapter implements (sketch); `Family` is evm | solana | aztec
   export interface ChainPort<F extends Family> {
     readonly prepare:  (call: Call<F>) => Effect<Unsigned<F>, ChainFault>;          // EVM: nonce, gas; Solana: accounts, blockhash
     readonly simulate: (tx: Unsigned<F>) => Effect<Simulated<F>, Refusal | ChainFault>; // always, before signing (evm#18, solana#19)
     readonly sign:     (tx: Unsigned<F>, signer: Signer<F>) => Effect<Signed<F>, KeyLocked | NoSuchKey>; // Aztec: prove, in the PXE
     readonly submit:   (tx: Signed<F>) => Effect<Submission<F>, Refusal | ChainFault>;
     readonly track:    (s: Submission<F>, level: Level<F>) => Stream<Included | Confirmed | Dropped | Reverted | Corrected>;
   }
   ```

   The first package is `@orthograph/chain-evm`, which is viem wrapped once (M6.05). `chain-solana` and `chain-aztec`
   come later. Where the family really differs, the differences live in the types:
   - EVM: a nonce and gas;
   - Solana: a blockhash and its expiry, the fee payer kept separate from the signers, and the accounts;
   - Aztec: proving in place of signing, and the sponsored fee.

   The follower (M6.09) is `track` run by an actor.
4. **Aztec has no "link a wallet to a person" by default.** Linking a private-membership account to a public person
   record would undo the privacy that is its point. The admin delivers a member's note to an address it was given
   privately. An Aztec link is left out of the wallet until a blueprint asks for one.

Kept from the frame:
- each wallet declares where its key lives, on a device or in a server's key store; no key is ever in plain text in a
  binding, a commit or a log (M6.18). The frame's "the server never holds a key" is dropped (F5);
- agents never link a wallet;
- the Node signer is an encrypted keystore file (Web3 Secret Storage v3);
- the browser signs through EIP-1193, which is an adapter.

**What the wallet needs from the framework.** Each item below is a ledger row, and the first plugin proves each one:
- plugin mounting (M1.01 to M1.10);
- runtime entries per host (M1.09);
- adapter calls as steps (M1.14), because the chain adapter is reached as `Blueprint.step.call`;
- **operations that run on the device**: `runs: "client"`, which the compiler refuses today (`describe.ts:108`) and
  which no slice lifts (ledger rows `LAH-02`, `G-10`). **Decided:** a new slice, **M1.27**, lifts the refusal for
  operations whose plugin supplies a host entry for `node`, `browser` and `world`. A generated client runs such an
  operation in-process, with its steps as spans.

What goes in the first version, and where it sits in the milestones, are forks for Aaron (F3 and F4 below).

**As built in M1.29** (18 to 19 November 2026; the full account is [M1-plugins section 8.2](M1-plugins.md)). What K7 left open, and what the
building decided, with the evidence in `design/evidence/M1.29/`:
- **The device half is built, the linked half is not** (M2.13). `create`, `import`, `keys`, `sign` and `send` are `runs: "client"`,
  with a signer per host: `node` (a Web3 v3 file), `browser` (EIP-1193), `keystore` (a server's key store, in M1 only a
  world-generated test key, used by a server operation through `Server.keystore`) and `world`. A host that has no such signer
  refuses as `KeyLocked`, saying why. F5 holds: each wallet says where its key lives (`signer`), and no key is ever in a binding, a
  commit or a log (a secret is `Redacted` from its first line, and `import`'s `source` is a secret field).
- **`confirmed` for a plain transfer** (Q3): no declared event exists to wait for, so the intent is the transfer itself,
  included and not reverted at depth one, a local chain's level. A real environment sets its level (`safe`) with its other
  settings when M6 gives the wallet its first event-bearing send.
- **The port is used as a library, not as a call step**: `send` imports `@orthograph/chain-evm/device` (the package without
  `Anvil`, plus `Keys`), so `prepare`, `simulate`, `sign`, `submit` and `track` are the port's own and the receipt spans are its own.
  Simulation is not an option anywhere in the wallet; the port refuses to sign what has not simulated.
- **Values**: `eip155:<chain>:<address>` is the only namespace built; a Solana or Aztec account is `None` from `Account.parse`.

## Taking from `@prb/effect-evm`: vendored, not a dependency

Said plainly: we copy the best parts of Paul Berg's library into our own chain adapter, instead of installing it. We
copy rather than install because we'll change its core anyway, and a copy we own follows our rules.

Aaron pointed at Paul Berg's `@prb/effect-evm` (MIT, Effect 4, built on viem) and asked whether to take from it. The
building agent's call, 18 November 2026: **vendor it, module by module, into `@orthograph/chain-evm`**, keeping the MIT
notice, never as a dependency. **Aaron approved it on 18 November 2026: "solid on the vendoring, let's do it".**
- **Now (M1.30).** The transaction manager and tracker (`tx/`, 42 KB), nonces (`nonce/`, 14 KB), viem error mapping
  (`core/errors/`, 45 KB) and event streams (`events/`, 32 KB): about 4,000 lines, the fiddly, tested parts.
- **Reshaped.** They move into our six-slot module shape, with every wait through `Timers`. `tx/manager.ts` is 20 KB, so
  it gets split. Errors are mapped onto `ChainFault` and the refusal lock, and events gain the block-hash window (Q6).
- **Ours.** Simulation is written by us, because theirs calls the Tenderly cloud API only and can't run on Anvil.
  Signers for the node keystore and the server key store are also ours, because theirs are for browser wallets.
- **Later.** Their browser wallet lifecycle (`wallet/`, 37 KB) and React hooks come in when we target React. Vendored files keep
  an upstream-notice header naming the source file and version, and are reshaped before they pass our lint. They have
  to be vendored too: once our core differs from theirs, their wallet module can't sit on top of it as a dependency.
- **Why not depend.** Measured on 18 November 2026 from npm and the repository: version 5.0.4 is 2.06 MB and marked beta, with three major versions in about two months. Our code rules
  (`Timers`, counted work, files under 250 lines) can't reach inside a dependency, and we'd change its core anyway.
- **Why not rewrite.** Replacement handling, receipt retries and viem's error zoo are tested there. Rewriting them
  throws that away.

## Open risks

- **Not tested anywhere:** real consensus finality, and a Solana fork. Anvil's `safe` and `finalized` are depth. The
  Solana validator is a single node. Aztec's finalized tip never moved in 240 s.
- **Two unexplained Aztec results:** a one-block rollback gave two outcomes in two runs (`aztec#21`), and the admin
  `setConfig({ realProofs })` toggle had no effect (`aztec#23`). Neither is relied on.
- **Hand-loaded Solana accounts** move Anchor's owner, discriminator and seed checks into generated code. Each is a
  security surface, tested per generator (`solana#17`).
- **The refusal lock is designed, not built.** Alias handling for a renamed error was only reasoned (`evm`, open
  risks).
- **Untried on Solana:** closing accounts to reclaim rent, address lookup tables, Token-2022, `remaining_accounts`,
  write-lock contention on one Proposal account, and the 1,232-byte and 64-account limits on a larger blueprint.
- **Untried on EVM:** proxies, several contracts per workshop, and non-standard ERC-20s such as USDT.
- **Aztec privacy:** the vote's choice is public calldata, and with few voters the tally's timing can point to the
  voter. The admin knows the member list. The portal says so on the vote's page.
- **Timings** come from one shared ARM64 Mac, with all three spikes running at once.
- **Anchor's TypeScript client** still needs `@solana/web3.js` 1.x while 3.x is current, and the first Solana build
  needs a 430 MB download (CI must cache it).
