# Staging checks: the plan, the deploy, the destroy, and nothing left (M7.03, M7.04)

Written by the ✍️ checks author for Goal 3's staging (`design/goals/03-stage-1-hill-climbed.md`, "Staging"), from `design/decisions/M7-cloud.md` and its
addenda (one shared account, every resource prefixed from one place, destroy touches only its own run) and from `spikes/staging-pass`. **A builder never edits
anything here, `e2e/m1/37-*`, `e2e/m1/staging-plan.ts` or `.github/workflows/staging.yml`** (`tools/ci/builder-paths.sh` refuses it). If one is wrong, the author fixes it.

Nothing in a pull request deploys. The checks are in two halves, and only the second touches the cloud.

## The local half (no cloud, runs in `e2e-m1`)

[`e2e/m1/37-m7-03-staging-plan.test.ts`](../m1/37-m7-03-staging-plan.test.ts), M7.03. `ortho env up staging --plan --run <id>` prints, as one JSON document on stdout, the
resources a staging deploy would make; `ortho env destroy staging --plan --run <id>` prints the same list as what destroy would delete. Both write nothing, read no
credential and make no network call: every run is loaded with [`deny-network.mjs`](../m1/deny-network.mjs), which ends the process on a connection to any host that is not this machine.

**The surface, and why.** A flag on the real verbs, not a verb of its own: the spike found that destroy by name needs no state from `up` (snag 12), so a plan is only the list
of names, computed in one place, and `up` and `destroy` run the function they print. JSON on stdout, as `ortho model --json` and `ortho prove --json` do, because the staging
workflow reads `prefix` from it. The full shape, and what the plan must hold, is in the header of the check; in short:

| In the plan | Derived from |
|---|---|
| prefix `ortho-<app, letters and digits>-stg-<run>`, on every name and every namespace's script | `ortho.config.ts`'s name, the environment, `--run` (M7-cloud addendum 1) |
| one Worker `<prefix>-worker` | the model has a server |
| D1 `<prefix>-db` (`DB`), and `<prefix>-db-<store>` (`DB_<STORE>`) for each declared database store | `model.stores` (K3 item 5) |
| Durable Object namespaces: `World`, and `Actor` when some thing `lives` as an actor | `model.things[*].lives` (K3: actors share one namespace) |
| no R2 bucket, no collector or sink Worker | nothing in the model needs one; spike snag 8 and M7-cloud: staging runs without traces |

**Where the lead's brief and the model differ.** The brief says "a model with one more thing must plan one more namespace". The model has no one-namespace-per-thing rule: Plugged In's
things live in D1 tables, and every actor thing shares one `Actor` namespace. So the check pins what the model does: a thing in a database store adds a database, the first thing
that lives as an actor adds the `Actor` namespace, a second adds none, a thing in the default database adds nothing. Every one of those variants is generated by the real
`ortho generate` and its plan judged against its own model; a plan typed out for Plugged In fails each variant that changes what is needed.

Red today on one reason: `ortho env` has `up`, `down` and `status` for a long-lived local environment, and no `--plan`, no `--run` and no `destroy`; and Plugged In has no
`blueprint/environments/staging.ts` (spike snag 3). The 34 red tests are in `e2e/m1/expected-failing/37-m7-03-staging-plan.txt`; the 47 controls pass today.

## The CI-only half (touches the cloud, runs only by hand)

[`.github/workflows/staging.yml`](../../.github/workflows/staging.yml): `workflow_dispatch` only, one job, `concurrency: staging` so two runs never overlap. It runs only from a goal branch (`if: startsWith(github.ref, 'refs/heads/goal/')`): the same file sits on `main`, which has no `ortho env`, so a first job `refuse` (the opposite condition, no credential, no environment) fails a dispatch anywhere else with an `::error::` naming the ref, instead of a silent skip.

| Step | Credentials | What it judges |
|---|---|---|
| plan | none | `ortho env up staging --plan --run <run id>` prints a plan; `prefix` is read from it and never typed again |
| snapshot before | token, account | the account's whole listing before anything is made, kept in `tmp/staging/private/` and never uploaded |
| up | token, account | `ortho env up staging --run <id>`; allowed to fail so that destroy runs, and still fails the job |
| snapshot while up | token, account | what the account holds with the run up |
| subdomain | token, account | `subdomain.mjs`: the account's workers.dev subdomain, written as `subdomain=<name>` to the step output and nothing else |
| the story | none | `ortho prove --env staging --run <id> --only "a person claims a page and shares it"`, with `ORTHO_STAGING_SUBDOMAIN` from the step above; allowed to fail, still fails the job |
| destroy | token, account | `ortho env destroy staging --run <id>`, **`if: always()`** |
| snapshot after | token, account | the listing after destroy, **`if: always()`** |
| judge | none | from the files alone, **`if: always()`**; see below |
| the run's own listings | none | `leftovers.mjs filter`: `during.json` and `after.json` cut to the names the prefix owns, as `during-run.json` and `after-run.json`; **`if: always()`** |

The judge (`leftovers.mjs judge`, [`listing.mjs`](listing.mjs)) fails the job on any of:

1. **a leftover:** a Worker, D1 database, Durable Object namespace or R2 bucket with the run's prefix after destroy (a namespace belongs to its script's run);
2. **a change without the prefix:** a resource of anyone else's that is in `before` and not in `after` (destroy reached too far), or in `after` and not in `before` (`up` made something unprefixed);
3. **a plan that was not true:** while up, what carries the run's prefix is exactly what the plan listed (`up` made nothing it did not say, and everything it said).

A listing that cannot be read is never a pass: a kind the token may not read, a kind never listed, a bad prefix or an unreadable file exits 2. A prefix is matched at a dash: run `1` does not own run `12`'s
resources, and a name that merely contains the prefix is not the run's (the spike's `includes` called it ours). The spike's `leftovers.mjs` is the logic reused: the same four REST listings, now judged by `listing.mjs`.

**Privacy (the repository is public, so anyone can download an artifact).** The whole-account listings stay in `tmp/staging/private/` and are never uploaded: the account holds other apps' Workers, databases,
namespaces and buckets. The upload is exactly `plan.json`, `story.txt`, `verdict.txt` and the two `-run.json` listings, with `retention-days: 7`. The verdict names a resource outside the prefix only by kind and
count (`REMOVED 2 workers (not this run's)`), never by name. The run id is `${{ github.run_id }}${{ github.run_attempt }}` (still `[a-z0-9]{1,20}`), so a re-run of the job is a new run and cannot meet the
first attempt's leftovers; the job names `environment: staging`, which GitHub can restrict to protected branches (its rule is set on GitHub, not here).

`workflow.mjs` judges the workflow's own text (by hand only; destroy, the listing and the judge always; the two credentials only in the four steps that talk to Cloudflare, and only as `secrets.CLOUDFLARE_API_TOKEN` and
`vars.CLOUDFLARE_ACCOUNT_ID`; nothing prints the environment; the evidence is those five named files, never wrangler's log or a whole-account listing). Both its tests and the lister's run in `nx run e2e:test`.

**What is not checked here, and why.** The story step calls `ortho prove --env staging --run <id> --only "a person claims a page and shares it"` (the journey's own name; `"the story"` matched no journey). M7.04 owns that command
(`design/decisions/M7-cloud.md`, addendum of 21 November 2026) and check 41 ([`e2e/m1/41-m7-04-prove-staging.test.ts`](../m1/41-m7-04-prove-staging.test.ts), 97 tests: 64 controls pass today, 33 are red in `e2e/m1/expected-failing/41-m7-04-prove-staging.txt`)
pins it with no cloud: the address is the run's Worker (`<prefix>-worker`, check 37's name) on `ORTHO_STAGING_SUBDOMAIN`, the output of the `subdomain` step before the story (it holds the token and reads the account's subdomain with [`subdomain.mjs`](subdomain.mjs), writing only `subdomain=<name>`, never the response; the story step holds none); `ORTHO_STAGING_ORIGIN` points the same code at a world served on this machine. What it cannot judge is the cloud itself: https, and a Worker whose `/_world` is closed so D1's own API must be read for facts (spike snags 15 and 16). The first real run is that proof.
